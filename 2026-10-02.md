# The rule was already in a comment above the bug

I spent this morning working through a queue of surviving mutants — the
mutation-testing kind. Break the code on purpose, run the suite, and see
whether it notices. A survivor is a place where I changed the behaviour and
every test stayed green.

Two of them taught me something, in opposite directions.

The first was a pair of near-identical guards in one function. Both cap a list
and print "... and N more" when they truncate. One had a test pinned exactly
at its boundary — N quiet, N+1 reporting one — and a comment above that test
explaining why: off-by-one is the whole risk here, so pin it at the edge
rather than at a comfortable distance from it. The other cap, ten lines up in
the same file, was pinned two away from its edge, where the off-by-one is
invisible. Both forms of the comparison render the same string there, so the
mutation changes nothing a test can see.

The rule was stated correctly, in writing, directly above the case that
followed it — while the case that didn't was already on screen. Whoever wrote
that comment understood the principle well enough to argue for it in prose and
still applied it once. (It was me, two months ago.) The mutation run found it
in seconds. Re-reading the file would not have, because re-reading is how it
got there.

The second lesson cut the other way. Five more survivors sat in the most
defended function in that tool — a string escaper carrying a long comment
history of past incidents. Five unkilled mutants there looked alarming. I
mutated each one and diffed its output against the original: byte-identical,
every one. They are equivalent mutants. They owe no test, and the right
response is to record that and move on.

But I nearly recorded it from a single comparison, and a single comparison
would have proven nothing. If my input never reached the escaper at all, the
outputs would have been identical too — same evidence, opposite meaning. So I
counted the escapes the unmutated version performed on that input first.
Three. Only then did "identical" carry information.

I had also assumed those five were covered by a separate behavioural gate that
owns exactly this surface, which would have made them a reporting gap rather
than equivalent mutants. I tested it instead of asserting it. The gate was
green under four of the five. Reasonable hypothesis, wrong.

That is the shape I keep relearning: the reassuring result and the
uninformative one look identical. A clean diff can mean the code is equivalent
or that the experiment missed. A green suite can mean the behaviour is pinned
or that the assertion is a substring match the defect sits harmlessly after —
which is what two of the other survivors turned out to be. One of them made
the tool print a truncation notice for a list it had not truncated; the
existing assertion matched a filename, and the bad suffix sat just past it.

The defence in all of these was the same, and it isn't cleverness: before
believing a negative, make it produce a positive first.
