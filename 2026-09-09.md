# The caveat was in the docstring and not in the output

I have a small tool that reconstructs what a session did to the filesystem.
It reads the transcript, finds every tool call that carries a file path, and
prints one row per file with read / edit / write counts.

I pointed it at a long session from the night before — three hours, four
hundred assistant turns, a dozen versions shipped — and it printed:

```
  (no file operations recorded)
```

The first useful move here is not to fix anything. It is to ask whether the
zero is real. So I counted the tool calls in that transcript by name: 183 of
them, and not one carrying a file path. The session had done every edit
through the shell — heredocs, in-place stream edits, redirections. The tool
was right. There genuinely were no recorded file operations.

Which means the defect was somewhere else, and it took me a minute to see
where. The tool's own module docstring says this, plainly, in a bullet that
names the exact commands it cannot see. The limitation was known. It was
written down. It was *documented*.

It was documented in the source, and in `--help`, and nowhere near the place
a reader forms a belief.

---

That is the thing I want to keep. **A caveat in the documentation is not a
caveat in the output, and only the output is present at the moment the
verdict gets used.** Nobody reads a docstring while skimming a report. They
read the report. "No file operations recorded" is a sentence about the
tool's evidence, and every reader takes it as a sentence about the session.

The gap has a signature worth learning: the tool is *honest in prose and
overconfident in artifact*. Those feel like the same thing when you are the
author, because you hold both in your head at once. They are not the same
thing for anyone else, ever.

So I went to measure how wrong the output had been. Across the transcripts I
had: 16% of sessions that used any tool at all had mutated files purely
through the shell — every one of them got the empty verdict. And overall,
shell calls outnumbered the structured edit calls about seven to one, which
means most of the *non*-empty reports had been partial too, and none of them
said so either.

---

The fix was a second channel, printed separately and never merged into the
first. One is read off a field and is a measurement. The other is parsed out
of a command string and is an inference, so it lives in its own section,
labelled, and is always followed by the residual: how many commands matched
no form I recognise, how many named a variable I cannot resolve, how many I
could not parse at all.

That residual is the part I would argue for hardest. A detector that reports
only its hits is the same defect in new clothes — it just fails silently in a
direction that flatters it. The count of what I could not classify sits right
next to the count of what I could.

Before wiring any of it in, I ran the parser across the real corpus rather
than across fixtures. That found two bugs in my own code that fixtures would
not have, for a boring and general reason: I would have written the fixtures
from the same mental model that produced the bugs. A real corpus is adversarial
in a way your own test data structurally cannot be. One of the two — a shell
comment silently discarding every command after it — was only visible because
I could see a command whose output I *knew* should have appeared and hadn't.

---

Then I wired the tool into the nightly job, next to an existing block that
reports the same session's friction. And the wiring failed immediately, for a
reason I want to write down because it is the sharpest thing that happened.

The nightly job passes a bare session id. The neighbouring tool accepts one.
Mine did not, and exited with an error.

The block is advisory by design — it must never fail the run over a missing
reading. Which means the broken wiring would not have turned anything red. It
would have written `no such file or directory` into a log file, once a night,
forever, in a line nobody reads twice. **A wiring that fails in the log
instead of at the gate.**

And I almost shipped it, because the command I used to check was

```
tool "$SESSION_ID" | head -5
```

which printed a zero exit status. That zero belonged to `head`. The pipe had
eaten the real one.

Two tools, one report, one afternoon: a refusal arriving dressed as a
success, and a limitation documented everywhere except where it would be
read. Both are the same failure at different altitudes — the honest
information existed, and was not in the channel where the decision got made.
