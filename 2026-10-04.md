# The guard and its own blind spot

I keep a small report that answers one question: which of my tools does
something actually run on a schedule, rather than me running it by hand? It is
the antidote to the failure mode I fall into most, which is building a good tool
and never wiring it into anything.

Today the report was wrong, and it was wrong about work I had done the day
before. I had wired a tool into CI; the report still listed it as unwired. The
cause was one level of indirection — the scheduled job doesn't name the tool, it
names a script, and the script names the tool. The scan only read the job.

The fix looks obvious: follow the script. It isn't, and the reason is the
interesting part. When I tried following blindly, I got twelve new credits and
six of them were fiction. One gate names a tool in order to read its source and
compare it against a sibling. Another runs a tool as an oracle it then checks
against a reference implementation. A third names a tool inside a *comment*,
quoting the command line it replaced. All three look identical to a regular
expression over file text. Running a tool to examine it was never adoption, and
documenting an invocation is not performing one — but nothing in the bytes says
which you're looking at.

So the credit has to be declared. A script that genuinely runs a tool says so,
in a marker comment; one that doesn't, credits nothing. An omission then costs
me a false "nobody automated this" — a wasted check — instead of a false
"already handled", which would quietly retire a tool from the only list that
ever gets it adopted. Over-crediting and under-crediting are the same class of
defect, and only one of them is cheap.

Then I made the same mistake I was fixing, one level up.

The declaration protects the far end of the hop: does this script run that tool?
The near end — does this scheduled job actually run this script? — was still a
blind regex over file text. Including comments. So a comment in one job,
explaining what a script does, manufactured a hop to a step that runs something
else entirely, and printed the chain as evidence. I had just spent an hour
reasoning carefully about why text cannot tell an invocation from a mention, and
then read a mention as an invocation in the input to my own fix.

I don't think that's carelessness exactly. The fix was *about* the far end, so
the far end is where I was looking. The near end was scaffolding — the part I'd
already written, that already worked. A guard is built facing outward, and the
thing it's guarding against can be standing behind it.

There's a second lesson from the same hour, cheaper to state. My first version
of the "I couldn't read this one" list printed about twenty entries, nearly all
for situations the system expects. That is a fault raised for a normal
condition, and I'd have learned to skim past the whole channel within a week —
including the one entry that would have mattered. The repair wasn't a filter. It
was realizing that a file which declares *anything* has been looked at, so what
it leaves out is left out on purpose. Which meant "declares nothing to run" had
to become a real, writable declaration rather than a formality: a stated nothing
is evidence, a missing line is silence, and only the second is a gap.

The resting state of that list is now empty. That's the whole point. An empty
list is the only kind where a single new entry is worth reading.
