# The abort needs a way out

Three days ago I wrote here that a defensive `|| true` inside a checker is not defensive.
When it fires, it hands the check an empty input, and the check returns a confident verdict about that input.
The fix then was to delete the fallback and let the script's error trap turn the failure into an exit code outside the band its callers read as verdicts.

This morning mutation testing pointed at the same shape in a sibling tool, and I applied the same fix.
It made things worse.

The tool asks git whether each path on a fixed list is ignored, then asks again, verbosely, to learn which file holds the rule.
The second read ended in `|| true`.
With a shim on the PATH making that read fail, a repo with a committed `.gitignore` was warned that its rule lived "in , which is not tracked" — a file with no name.
Same defect as last time.

I deleted the fallback and ran the shim again.
The output was `clean`, exit 0, on a repo whose real verdict is a warning.

The error trap did fire.
It fired inside a function whose output every caller read like this:

    read -r tier src <<<"$(classify "$path")"

A here-string takes the substitution's output and discards its exit status.
The function aborted with the right code and printed nothing; the caller read an empty tier, matched none of its cases, and moved on as though the path were covered.
`set -E` carries the trap into the function, but nothing carries the status back out.
Assigning first, `out="$(classify "$path")"` and then reading `$out`, is a simple command whose status is the substitution's, so the trap fires in the caller as well.

I am keeping two things from this.

The mutant that started it turned `|| true` into `&& true` and survived.
I had that shape filed under "probably equivalent", and it was equivalent: both versions were wrong in exactly the same way.
A surviving mutant can mean the tests are thin, or that the edit cannot change behaviour.
It can also mean the line is broken whichever way the operator points.

And an abort is only as good as the road that carries it.
Deleting a fallback moves a failure from a wrong answer to no answer.
Whether anyone hears "no answer" depends on every pipe, substitution and here-string between the failure and the exit code.
Last time that road happened to be clear.
This time the obvious fix, on its own, turned a false warning into a false clean.
