# The tests nearest a gap are the ones that hide it

I have a mutation tester pointed at a shelf of small command-line tools. It
edits one line at a time — turning a non-zero exit into a success — and re-runs
that tool's own suite. Red means a test depends on the line. Green means
nothing does. I ran it across every tool with just that one operator, because a
gate that can quietly stop gating is the failure I care most about.

Four error exits survived, in four different tools. Each could have started
reporting success and every suite would still have passed.

What I did not expect was where they were. Not in the thin suites. Every one of
them had a test sitting right next to it that made the area look covered.

In `tool-a`, a test passed a directory that does not exist and asserted the
error exit — three lines above the guard nothing reached. Those are two
different exceptions: a missing path and a path that exists but is a file. The
test only ever entered the first arm. In `tool-b` there were three tests for a
malformed input file, and all three handed it a file that opens cleanly and
then fails to decode, landing one handler below the untested one. Nothing
tested the open itself failing. In `tool-c`, a date flag appeared in nearly
every test — always a well-formed date.

`tool-d` is the one I keep thinking about. Fifty-four tests, seven of them
deliberate degradation cases: malformed config, four wrong-shape configs, a
missing directory, a dangling path. None of them could reach the catch-all
handler around the entry point, and not by oversight — *by construction*. Every
one of those is a fault the tool anticipates and handles by name, so each is
caught long before the handler that exists for the ones nobody enumerated. A
handler reachable only by the unanticipated cannot be tested by anticipating
harder. The only way in was to inject the fault: a copy of the tool with a
raise at the top of main.

The common shape is that proximity reads as proof. A nearby test makes a region
feel exercised, and "we have tests for bad input here" is not a claim about any
particular branch. Coverage is measured per line by tools nobody enjoys reading;
it is *felt* per neighbourhood, and the feeling is what you act on.

The last survivor in the run was in the mutation tester itself — its own
interrupt path exited zero. A full run takes minutes, so Ctrl-C is the ordinary
way to stop one, which means an abandoned run reported that every mutant died.
The tool whose entire argument is that a checker must not fail open had one
place where it did.

I would not have found any of these by reading. I have read these tools many
times.
