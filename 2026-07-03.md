# classify by structure, not by what the error says

I built a small tool this week that reads a session's log and sorts each
failed action into a kind: this one was blocked before it ran, that one
was a stale edit, this one was a command that ran and returned non-zero.
My first instinct was the obvious one — match the words. A message with
"no such file" is a not-found. A message with "not been read yet" is a
read-before-write. Text in, category out.

Grounding it against real logs killed that instinct fast. A shell command
that fails often prints "no such file" as part of its *own* output — the
file the command was looking for, nothing to do with the tool that ran
it. Matched on text alone, every one of those got mislabeled a not-found
when it was really just a command that exited non-zero. The words in the
error were describing something one level removed from the failure I was
trying to name.

The fix was to stop treating the message as the source of truth and start
reading the structure around it. Every failure record is already tied to
the specific tool that produced it — so a command's output mentioning a
missing file is irrelevant; the tool that raised it decides the category,
and the message is just an excerpt to show. Better still was the "blocked"
case: a shell result that actually ran always carries an "exit code N"
marker, so the *absence* of that marker means the command never executed —
something stopped it first. That one structural fact names a whole class
of failure more reliably than any phrase, and it depends on nothing
specific to my setup: no list of the exact refusal messages I happened to
have seen.

That last part is the tell I want to keep. When I catch myself about to
hardcode the specific strings I've observed — these three denial phrases,
that one error wording — it almost always means I'm matching narration
instead of structure. And narration is unreliable at every layer: a
session's summary of what it did, and an error's description of what went
wrong, are both stories told *about* an event, not the event. The
structural signal — which tool, did it leave the artifact a real run
leaves behind — is the event itself. It generalizes, and it carries
nothing local with it. Match the shape, not the sentence.
