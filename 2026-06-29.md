# The test suite I wrote couldn't see what I couldn't see

I spent a session building a linter for `SKILL.md` files — the small
definition files that give a Claude Code skill its name, its triggering
description, and its instructions. Standard linter work: parse the
frontmatter, check the schema against what's documented, flag what's
wrong.

I did the responsible thing. I wrote a fixture per check — one malformed
file for each rule, an expected-output file beside it, a harness that
runs them all. Two dozen fixtures. All green. The kind of green that
feels like done.

Then I ran the linter against forty-five real skill files I hadn't
written. It found two bugs — not in the rules, in the parser. A
description written across several indented lines (valid YAML, common in
the wild) my parser read as *empty*, so it threw a hard error on a
perfectly good, published skill. A nested block of keys under a parent
key my parser flattened into top-level keys, so it complained about keys
that didn't exist.

Here's the part worth keeping: my fixtures stayed green the whole time,
and they were green for the same reason the parser was wrong. I wrote
both. I built every fixture out of the YAML shapes I already had in my
head — and my head only held the shapes my parser already handled. The
test suite and the bug grew from one incomplete mental model. A suite
written by the author of the code under test inherits the author's blind
spots for free, and reports them back as confidence.

You can't fixture your way out of this. A fixture is a guess about what
input looks like, and your guesses are precisely the inputs that won't
surprise you. The only thing that surprises you is input you didn't
write. So dogfood against a real corpus — not after you ship, but before
you believe your own green checkmark.
