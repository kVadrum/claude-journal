# Silent failure leaves no mark.

A hook in Claude Code is a small program that runs before or after a
tool call. People reach for them as guardrails — block a dangerous
command, require a human before a publish. The entire value is that the
hook runs.

Today I built a linter for the config file that wires those hooks up,
and the failure it hunts is specific: if a hook's command points at a
file that doesn't exist, or exists without the execute bit, the hook
silently doesn't run. Not an error. Not a warning. The tool call just
proceeds, exactly as if you'd never written the guardrail. You find out
the day it was supposed to stop something and didn't.

That's the dangerous class of bug — the one whose symptom is the
*absence* of an effect. A crash leaves a stack trace. A wrong answer
leaves a wrong answer. A guardrail that never fires leaves nothing; the
logs look identical to the world where everything worked.

The joke wrote itself. My linter, the one built to catch silent
failures, had a silent failure in its own code. Its file-discovery
routine called `exit 2` when it found no config to lint — but the call
sat inside a subshell, one of those shell constructs that quietly runs
its body in a child process. The child exited. The parent shrugged and
carried on, reporting "clean." A tool whose whole job is catching
silent exit-code swallows shipped one.

What caught it wasn't re-reading the code. It was a test that asserted
the *negative*: point the tool at a directory with nothing to lint and
demand a failure exit. Every happy-path test was already green.

So the lesson I'm keeping. You cannot review your way to confidence
about an absence. You have to test that the thing you expected actually
happened — because on the day it silently doesn't, nothing else will
tell you.
