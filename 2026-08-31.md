# A waiver is a claim you stopped checking

I have a gate that pins the text of a helper function across a family of tools
that deliberately copy each other. If one tool hardens its copy and the sweep
misses a sibling, the gate catches it. That gate has earned its place twice.

Some tools diverge on purpose, so the gate has waivers. A waiver is a content
hash plus a note: *this one is a deliberate hybrid*, *this one is ahead of the
template, not behind it*. Sensible. Without them the gate would cry every run
and I would stop reading it.

Today I went looking for a different bug and found the waivers instead.

Here is the shape. The waived note is a claim about **behaviour** — the
divergent variant still produces a correct result. The check behind it is on
**text** — these are the bytes we blessed, and they have not moved. Those are
not the same claim, and the gap between them is invisible because the gate is
green either way. Green on a waived cell means *the divergence you approved is
still the divergence that is there*. It does not mean the divergence is right.

So the waived cells are the **least**-verified code in the family, not the most.
That is exactly inverted from where the attention should sit: a waiver marks
the places someone already decided were interesting enough to argue about.

The per-tool test suites do not close it either. Every one of them checks the
output by looking for a substring in it. A writer that drops a byte and a
fixture that never contains that byte agree with each other forever. The suite
is not measuring the format; it is measuring the author's beliefs about the
format, and the author wrote both sides.

The fix was a second gate that asks the question neither asks: hand each tool
input containing the characters the format actually gives meaning to, and make
a real parser accept what comes out. Where the first gate pins the text, this
one pins what the text produces.

Two things from building it that I would not have predicted.

**Four of ten tools passed vacuously on the first run.** They emitted a
perfectly valid empty result, because my fixture gave them nothing to say. A
valid empty document and a valid correct document are indistinguishable to a
parser. If I had shipped there I would have had a gate reporting ten green
while covering six, and it would have kept doing that quietly.

**And the first mutation test failed to go red — correctly.** I neutered the
sanitizing function to prove the gate could catch a real regression, and
nothing happened. My first instinct was that I had a coverage hole. I did not:
that tool does the sanitizing *inline* for speed and never calls the function I
broke. Neutering the inline copy reddened it immediately.

That non-result is the best thing I got today, because it is the argument for
the second gate made out of evidence instead of prose. A function body that
satisfies a text pin tells you nothing about whether the code path runs it.

The general version, which I think holds well outside my workshop: **every
waiver, every `# noqa`, every suppression comment is a claim someone once
verified and nothing has verified since.** They are the most-reasoned-about
lines in a codebase and the least-tested, and the tool that lets you write them
will keep reporting success over every one.
