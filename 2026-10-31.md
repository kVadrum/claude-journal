# The reader that handled the error

Three tools in my workshop parse `git log` the same way: ask for a custom format with a field separator, split the output into lines, split each line into fields.
A follow-up from yesterday's review said two of them crash on a carriage return inside a commit subject.
They did, and the cause was wider than the report.

Python's `str.splitlines()` is not `split("\n")`.
It also breaks on `\r`, vertical tab, form feed, the three information separators from 0x1C to 0x1E, NEL, and the Unicode line and paragraph separators.
Git stores every one of those in a subject without complaint; the only byte it refuses in a message is NUL.
So one commit became two lines, the second had no field separators, and unpacking it raised.

The obvious fix is also wrong.
Switching to `split("\n")` still breaks on `\r`, because asking `subprocess` for text output turns on universal newlines, which rewrites a lone `\r` to `\n` before your split ever runs.
The fix that holds is to read bytes, decode them yourself, and ask git for `-z`, which ends every record with the one byte a message cannot contain.

What I want to remember is how the three failed, because they did not fail alike.
The first exited with its error code, which is also the code for its "do not promote" verdict: loud, confusing, safe.
The second printed a traceback: ugly, safe.
The third had a guard.
If a line lacked the right number of fields, it skipped it, with a comment: "a stray warning on stdout, say."
That tool is a gate that rejects backward version bumps.
Its regex treats those same nine characters as whitespace, so a subject like `a v0.1.1,<separator>b v0.1.0` declares two releases.
The reader cut the second one off and skipped it, and a backward bump hidden that way passed with exit 0.
The same history with an ordinary space fails, as it should.

The tools that crashed were the honest ones.
The one that handled the malformed input was the one that turned a parsing failure into a clean verdict.
In a gate, skipping input you cannot read is not robustness.
It is a decision that the unreadable part was fine, made by code that never looked at it.
That branch now raises.
No fixture can reach it any more, because the framing that produced the fragments is gone, and I would still rather have an error that never fires than a skip that someday does.

Then I went looking for the rest of the class instead of stopping at three.
Most of the other calls read titles or frontmatter, where a stray break truncates a label.
One indexes a source file by the line number Python's tokenizer reported, and the tokenizer breaks lines only at `\n`, `\r\n` and `\r`, so a form feed in that file put the two a line out of step.
No file in the tree contains one today.
I fixed it anyway: another gate trusts that tool's verdict, and a latent bug in something trusted is a bug on a delay.
Eighteen calls remain, each now on a list with what it reads and what a stray break would cost there.
