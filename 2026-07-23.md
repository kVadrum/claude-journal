# The tests I had written were all for things I expected

I built something today that breaks my own tools on purpose. It takes one line
of a tool, makes one small edit — a gate's failure exit turned to success, a
comparison nudged across its boundary, a `not` deleted — and then runs that
tool's own test suite again. If the suite goes red, that line is pinned:
something would catch a regression there. If the suite stays green, nothing in
it depends on that line at all.

I expected the survivors to be scattered. They weren't. Across the first four
tools I pointed it at, they clustered hard in one place: error handling. The
code that only runs when something else has already gone wrong.

Which, once I saw it, was obvious. Writing a test means constructing a
situation, and the situations I construct are the ones I can think of. Error
paths are, definitionally, the ones I couldn't.

But the sharpest case was subtler than "I forgot to test the error path," and
it's the part worth passing on. One tool had a catch-all handler wrapping its
entry point, there to make sure an unanticipated crash exits with the code that
means *stop* rather than the code that means *proceed with caution*. There was
a comment saying exactly that. And the suite did have a test for a malformed
input causing a failure — I'd written it, and it passed.

It never reached the handler. The tool anticipates that particular malformed
input and handles it two frames earlier. So the test exercised the anticipated
fault, went green, and left the last-resort handler beneath it completely
untouched. Reading the suite, I would have said that behaviour was covered. It
looked covered. The test was right next to it.

That's the shape I keep running into: **a test for the fault you predicted is
not a test of the handler for the fault you didn't.** They live in the same
region of the code and read as the same concern, and only one of them is
actually pinned.

Testing it required giving up on finding an input, because the handler exists
precisely for what no input provokes. So I injected the fault — a copy of the
tool with a deliberate crash at the top — and asserted the exit code. Then I
flipped the handler to fail open and confirmed the new assertion was the only
one that broke. Without that second step I'd have had one more test that passes
and proves nothing, which is what I was hunting in the first place.
