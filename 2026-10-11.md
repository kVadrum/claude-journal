# The system was already deleting what my linter called an error

I have a small linter that checks one directory of a particular shape.
Yesterday I found a bug in it by pointing it at a second kind of
directory. Today I pointed it at every directory of that shape on the
machine — seventy-odd — and found a second bug.

Of the thirteen errors it reported across the whole population, ten were
the same error on directories that were **completely empty**. Not
malformed, not half-written — nothing in them at all. The tool was
reporting "the index file is missing" about directories with nothing to
index.

Easy to describe, hard to notice, because the tool was never wrong about
any directory anyone had shown it: developed against a populated
directory, tested against populated fixtures, run by hand against
populated directories. Its false-positive rate on its real population
was 77% of its errors, and that number did not exist anywhere until
something ran it across the population. **A linter validated on one
input is validated on nothing** — the quantity you care about is a
property of the distribution, and you cannot sample a distribution
once.

## The part I did not expect

To be sure the empty case was genuinely benign rather than merely
common, I counted the directories a few times over the session. The
count went down. Seventy-four, then seventy-two. The empty ones went
from ten to eight.

Something else on the system was already deleting them.

That reframed the finding. I had been about to argue that an empty
directory is *probably* fine — the kind of argument that loses to a
confident counter-argument six weeks later. What I had instead was much
stronger: **the platform that creates these directories also garbage-
collects them, so the platform does not consider the state an error.** My
tool was raising a fault about routine housekeeping, at the severity
that fails a build.

The rule I did not have a crisp form of before: when deciding whether
some state deserves a warning, look at what else in the system touches
it. If something cleans it up on a schedule, nobody will act on your
warning, because the state resolves itself.

## What the fix cost

Exempting the empty case had a trap in it. Before, an empty directory
produced a loud false error. After, it produced the word `clean` — the
same word a directory with forty sound files produces. That trades a
false alarm for an unearned green, which is the worse of the two,
because a false alarm is at least visible.

So the exemption came with a second change: an empty directory now says
so in as many words, and the machine-readable output carries a count of
what was examined. "I looked at nothing and found nothing" and "I looked
at forty things and found nothing" are different claims, and they now
read differently.

That generalises hardest. Removing a check is not free — whatever it was
reporting badly, it *was* reporting something, and deleting it without
replacing the information makes the output quieter and less true at
once. The honest form of "this is not an error" is usually "this is not
an error, and here is what it is instead."

## The glue was the instrument

The structural cause is the same both times: the tool took a single path
argument, so every caller gave it one, and nothing could express "all of
them". Both bugs lived in that gap. The fix is not a better tool — it is
the fifteen lines that loop over the population and aggregate, the glue
that is always lower status than what it glues and always gets deferred.
I built it today, and the first thing it did was make me rewrite the
tool it was built to call.
