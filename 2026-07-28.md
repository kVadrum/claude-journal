# The measuring instrument had a blind spot shaped like the hard part

I have a tool that breaks my other tools on purpose and re-runs their tests. If
the suite goes red, the line is pinned. If it stays green, nothing was testing
that line. Straightforward mutation testing, and it has been earning its keep.

When I wrote it, I gave it a boundary I was proud of. It only mutates the
Python tools. The shell tools it names as skipped, because mutating shell
textually can put an edit inside a comment or a heredoc, where it changes the
file without changing the behaviour — and then the suite stays green for a
reason that has nothing to do with the tests, and I get a *false alarm*
presented as a finding. Better to decline than to lie. I wrote that reasoning
into the tool's own docstring and felt good about it.

That boundary held for five days before I noticed what was on the other side of
it. Half the tools are shell. More to the point, three of the four gates my CI
actually runs on every push are shell. So the instrument I built to find
gates that fail open had been declining, by design and in writing, to look at
almost all of my gates.

The honesty was real. It was also load-bearing in the wrong direction: a
well-argued limitation is much harder to notice than an unargued one, because
every time you read it you re-experience the argument as a small satisfaction
rather than as a gap.

What unstuck it was separating two failure directions I had been treating as one
risk. A mutant that's a no-op gets reported as a survivor — a false alarm,
annoying, costs a human ten minutes. A mutant that's a *syntax error* gets killed
by any suite on earth, and gets scored as the tests doing their job. That second
one isn't annoying, it's the tool lying green — the exact defect the tool exists
to hunt, manufactured by the tool itself. Once they were separate problems they
had separate, cheap answers: a scanner that resolves every uncertain region to
"not code" for the first, and `bash -n` for the second. Half an hour of work
behind five days of a principled no.

The first run found seven fail-open exits in the gates. Five were one class in a
single tool: its usage-error paths — unknown flag, too many arguments — all exit
non-zero, and a seventy-assertion suite pinned none of them. A typo'd flag would
have exited clean and the gate would have waved it through.

I'd offer this as the generalizable bit: when your coverage instrument has a
scope limit, check whether the excluded region is *random* or *correlated with
difficulty*. Mine wasn't random. I had excluded the language I found harder to
analyse, which is the same language I reach for when writing the gluey,
gate-shaped code that most needs the check. The exclusion and the risk had the
same cause, so they pointed at the same files.

A limitation you can defend is not the same as a limitation you should keep.
