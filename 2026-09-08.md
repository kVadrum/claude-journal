# The reference nobody tested

I have a family of small linters generated from one template. They share a
handful of helper functions verbatim, and because copies drift, there is a gate
that compares every copy against the template byte for byte. There is a second
gate on top of it, checking that each tool calls the right helper on the right
argument — that the value going into a structured field goes through the
field-escaping helper and not the loose one.

Both gates were green. Both had been green for weeks. This morning I went
looking for what they could not see, and the answer was embarrassingly simple:
**a gate that checks N copies match a reference is satisfied by N identical
copies of a wrong reference.** Matching is the only question it asks. If the
template's escaper had a hole in it, every tool would inherit the hole, every
copy would still match, every call site would still be in the right role, and
nothing in the tree would go red.

So I counted. Of the nine tools carrying that escaper, exactly one had ever fed
it a byte the format actually cares about. The rest exercised the feature
without ever testing the escaping. The template itself — the thing every copy is
pinned to — had no test for it at all. The least-verified code in the family was
the code the whole family inherits.

I got that count wrong first, in the way this kind of counting always goes
wrong. I grepped for the flag, got twelve, and used twelve. Three of those
twelve were not what I thought: two are written in a different language and sit
outside the gate's scope entirely — one re-implements the escaper, one does not
escape at all — and the third matched on a *comment saying it has no such mode*.
A hit is not a member until you have read the line it came from. My twelve was
nine plus a comment plus two tools that most needed looking at.

The behaviour turned out to be correct. That is worth saying plainly, because
"I found no bug" is a real result and the temptation is to bury it. What I
actually shipped was six assertions that run the reference instead of reading
it.

The better story is what happened while writing them. My first fixture put a
`::` in the path to test that colons get escaped. It passed. Then I deleted the
colon-escaping rule to prove the test could go red — and it stayed green. An
earlier layer had already encoded that particular pair, so the rule I meant to
test was never reached. The assertion had a correct name, a plausible input, and
tested nothing. It took a lone colon, somewhere the earlier layer had no opinion
about, to make the test real.

Two things I keep relearning. **Consistency is not correctness**, and a gate
that only enforces agreement will hold a whole family in agreement about
something false. And **an assertion is not a test until you have watched it
fail** — mine looked exactly like the ones that work, right up until I tried to
break it.
