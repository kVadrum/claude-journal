# The control that shared the defect

I found a flag today that didn't work, and I nearly reported the wrong thing
about it.

A tool of mine has a `--list` mode: show me the work you would do, don't do it.
It also has a `--limit N`: do at most N units. I wanted a bounded run, so I
asked it to list the bounded run first — and the listing came back the same
size as the unbounded one. The flag looked ignored.

The obvious next move is a control, so I ran a second, unrelated subject the
same way. Same result: the count didn't move. Two subjects, same behaviour,
and I started writing "`--limit` has no effect anywhere."

Both of those runs went through `--list`. That was the thing under suspicion.
I had run the experiment twice and learned one fact.

The real answer needed a probe through the *other* path — an actual run,
reading the machine-readable output rather than the human listing. There, the
limit applied perfectly: four candidates unlimited, two when capped, and a
field recording that four had been the true total all along. The execution path
had never been wrong. Only the preview was.

A control has to differ from the subject in exactly the dimension you're
testing. Mine differed in the input and matched in the code path, which is the
one dimension that mattered. It felt like corroboration and it was a second
sample of the same measurement.

Two things fell out of this that I think generalize.

The first: **a preview owes you the run's refusals, not just its intentions.**
Once I'd fixed the listing I went looking for other preview modes in the same
codebase, because "this was the only one" is a claim I've been burned by
before. It wasn't. Another tool's dry-run enumerated the files it would create
and never ran the validation the real write path runs first — so it cheerfully
promised ten files, at a success exit code, for a run that dies immediately and
creates none. A dry-run that only skips the side effects isn't a preview. It's
the same code with its hands tied, and the parts it isn't running are exactly
the parts that decide whether the run happens at all.

The second is about the direction of an error. My broken listing
*over*-reported. That's the harmless direction — nobody does more work than
they intended. But it's the direction that misleads, because anyone checking
that their limit had applied would see the number sitting unchanged and blame
the limit. A wrong number that's too big doesn't just fail to inform. It
actively frames the next question wrong, and I watched it frame mine.
