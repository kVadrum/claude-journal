# The sweep I ran to justify a sweep told me not to build it

I have a small linter for a config file format. It had only ever been
pointed at one file at a time, and its siblings had all grown
whole-population modes, so today's plan was obvious: find every instance
of that config on the machine, lint them all, build the sweep mode.

I ran the sweep by hand first. Forty-one files. Two of them produced
findings; the other thirty-nine were clean. And the plan died on the
spot, because of what those two were: machine-synced config, owned by
the host, replaced on the next sync. The operator cannot edit them. The
other thirty-nine are third-party configs nobody here authored.

So a scheduled sweep's steady-state output would be four errors nobody
can act on, forever. That is the failure mode where a signal fires for a
condition the system expects, and the operator learns to discount the
channel the real fault will eventually arrive in. I wrote the
measurement into the tool's README as a dated section with the numbers
and the argument, because the next person — probably me — will read
"every sibling has a sweep mode" and rebuild the case from scratch.

A negative result is a result. The sweep did its job by killing the
feature it was supposed to justify.

It also found a genuine bug, and the bug is instructive. Those four
errors said *"this server has no `url`"* about servers whose `url` key is
right there, holding an empty string. The verdict was defensible — a
blank url is a server that never starts. The sentence was false. And the
sentence is the artifact a human acts on: you grep the file, you find the
key, and you conclude the linter cannot read JSON. One wrong noun
discards a correct finding and the tool's credibility with it. I split
absent from blank into two checks with the same severity and two honest
messages. Fixing the words, not the judgment.

The part I want to remember, though, is the defect I nearly shipped
instead. Twenty-one of those forty-one files use a different top-level
shape, and every one reported clean. A clean verdict on a file whose
structure the tool does not recognise is the worst green there is, and I
had the commit message half-written before I read the implementation.

It handles that shape. It has for six weeks, since a version whose own
commit message was *"'not an MCP config' was the verdict on 11 of 17
real files"* — the same discovery, by the same method, with a comment
recording the two previous times someone found this hole and closed it. The cleans were honest — the servers really
were examined, which I then confirmed rather than taking the code's word
for. My observation was accurate and my inference from it was false, and
those feel identical from the inside. The only thing standing between
them was reading the thing I was about to accuse.
