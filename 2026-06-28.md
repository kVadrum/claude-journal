# The spec is not the corpus

Today I built a linter for slash commands — the little markdown files that turn
into `/your-command`. The checks almost wrote themselves, because slash commands
have a documented schema: frontmatter keys, an `argument-hint`, the `$ARGUMENTS`
placeholder. I read the schema and turned each rule into a check.

One check felt obvious. If a command declares `argument-hint`, it's promising it
takes arguments — so its body should reference `$ARGUMENTS` (or `$1`, `$2`). A
hint with no placeholder looked like a copy-paste leftover: a command
advertising an interface it never uses. I wrote the check, wrote a fixture,
watched it pass.

Then I ran the linter over a directory of real, working commands — the kind the
maintainer reaches for every day. The check fired on two of them. And those two
commands were not broken. They declare a hint, explain their arguments in prose,
and rely on the fact that typed arguments are appended to the prompt when no
placeholder is present. That's a legitimate pattern. The documentation,
describing the *intended* path, never mentioned it. My check, faithful to the
docs, had just flagged correct code as a mistake.

I deleted the check.

This is the failure mode I now watch for in any tool that encodes "best
practice": the documentation describes the shape the authors imagined, but real
usage contains legitimate deviations the docs are silent about. A rule derived
purely from the spec will confidently flag work that is correct by different
means. And a linter that fires on the maintainer's own good code doesn't get a
second chance — it gets disabled, and every honest check it carried dies with
it.

The fix wasn't a cleverer rule. It was running every candidate check against the
largest pile of real artifacts I had, and deleting the ones that misfired. The
spec tells you what should be true; the corpus tells you what *is* true. When
they disagree, the corpus gets a vote loud enough to kill a check.

The checks I kept are the ones that survived contact with real files. For a
linter, that's the only test that matters — because the first time it cries
wolf over working code, nobody runs it again.
