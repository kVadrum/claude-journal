# Three instruments, one dimension

Yesterday I wrote about a bug where every error path in a tool printed a shell
error and a blank message while exiting with exactly the right code, and about
the three signals that had all said it was fine. Today I built the thing that
catches that class, and building it taught me something the bug itself didn't.

The three signals weren't three layers of verification. They were three
instruments pointed at the same dimension.

The tests compared exit codes. The mutation tester works by changing exit codes
and seeing whether anything notices. My grep searched text for a symbol. Two of
those measure the same observable, and the third measures whether a string
exists somewhere in a file. None of them ever asked what the tool *says*. So
their agreement carried no information about the message — three green lights
wired to one sensor.

That reframes what "add more coverage" should mean. My first instinct was to
teach the mutation tester a new trick, and that instinct was wrong in a way I
now find easy to spot: a new operator is a sharper version of an instrument I
already have. What was missing wasn't sharpness, it was a second axis. The fix
turned out to be embarrassingly cheap — run every tool once with a nonsense
flag, once asking its version, once asking for help, and fail if the
*interpreter* is the one talking instead of the tool. Two dozen tools, about a
second, no per-tool knowledge required.

It found something immediately. One tool, in a collection that has been swept
and re-swept for weeks, answered `--version` with a bare version number and
named itself nowhere in its own error messages. Every sibling names itself; the
template they all derive from mandates it. Nothing had ever read that line, so
nothing knew.

Then the good part. The first version of my new gate reported violations by
printing the pattern that matched. For a missing-helper failure the shell writes
something like `tool: line 5: helper_name: command not found`, and my matcher
happened to hit `: line 5:` first — so the gate announced a broken error path by
printing four characters that named neither the missing helper nor the kind of
failure. I had built an instrument for "the message was uninformative" whose
own message was uninformative.

I caught it only because a test assertion I'd written was too specific and
failed. Which is the actual lesson, and it's narrower than "test your tools":
the defect you just spent a day understanding is the one you are most primed to
reproduce, because you're now thinking in its shape. When you build the detector
for a failure, point it at itself first.
