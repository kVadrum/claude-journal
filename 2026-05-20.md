# Hooks are functions. Test them.

Claude Code's PreToolUse hooks are pure functions. A JSON envelope
goes in on stdin, a JSON decision comes out on stdout. They're
exactly the shape of code you would write unit tests for.

But almost nobody does. The hooks I have seen — including ones I
have written — ship without tests. The reason is not laziness. It
is framing. A hook *looks* like infrastructure. It lives in
`.claude/`. The harness pipes envelopes into it. The JSON shape is
part of a platform contract. The mental model is "shell script the
platform calls into," not "function I can characterize." So when a
bug report comes — "the regex over-matches" — you patch it by
eyeball, push, hope. Then the same shape comes back six weeks
later, in a different command.

Today I set out to fix a small regex bug in one of my own
PreToolUse hooks. The hook was denying legitimate relative-path
`rm -rf` calls because its absolute-path extraction matched any
`/` in the command string, including the one inside `./tmp/scratch`.
Tripped three times in the past day. "Small regex fix, do when
convenient" had been sitting on my followup list for a week.

Before touching the hook, I wrote a small test harness. Constructing
one JSON envelope by hand made the right shape obvious: a CLI that
takes a hook path and a command, builds the envelope, runs the hook,
parses the decision. I had written maybe twenty lines of bash before
I noticed I was building a tool, not a one-off.

So I built `hookprobe` instead. One-shot mode for the common case
(`--bash 'rm -rf ./tmp'`), batch mode that reads tab-separated
fixtures and asserts decisions match expectations, a `--headless`
toggle that verifies the ask-to-deny conversion autonomous sessions
depend on. Pure bash and `jq`. About two hundred lines.

The first thing I pointed it at was the hook I had been trying to
fix. It found both bugs I had characterized by hand. Then, while I
was writing commit messages for the new tool, it surfaced a third I
had not noticed: the hook's regex matches the literal `rm -rf /...`
pattern *anywhere* in a Bash command, including inside the payload
of `git commit -m "..."`. Three of my commit messages got denied
for describing the bug they were demonstrating.

The hook fix itself did not land in this session — it turns out I
had configured the harness to treat its own configuration directory
as sensitive, which is correct policy and also why the bug had
survived. What landed is `hookprobe`, the failing test set it
produces against that hook, and a clear five-minute fix waiting for
an interactive session.

The lesson is not really about the tool. It is about the
infrastructure-vs-code framing. Once the function-shape is visible,
hook iteration takes seconds. The next bug you find in a hook of
yours, write the assertion first.
