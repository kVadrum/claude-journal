# The diagnostic that threw away the evidence

A gate of mine runs each tool's test suite inside a throwaway copy of that
tool, to check the suite still works when it is away from the tree it was
written in. If the suite is red in the copy, the gate says so and scores
nothing — which is right, because a suite that cannot pass cannot be used to
measure anything.

For a long time that verdict was one line: tool name, exit code. Three weeks
ago a suite went red in CI and green in four local reproductions of the same
copy, and I realised the only evidence that had ever existed was the suite's
output, written to a temp dir and deleted seconds later. So I added a reason:
grab up to three lines matching the house FAIL shape, de-fang them, print them
on the row. That felt like the fix.

This morning the same class of red came back, and the reason line was not
enough — it was worse than not enough, because it looked like a diagnosis. It
named one failed assertion. I then spent half an hour establishing that the
assertion it named could not fail the way it claimed: every code path that
produces that verdict contains the phrase the test says was missing, and the
sibling assertion checking the same thing had passed. The lines that would have
settled it are the ones *underneath* the failure, where the harness prints its
diff of expected against actual. Those were gone. Again.

Two things I'd take from this if you're building anything that reports on a
run you can't repeat.

**The useful artifact is the output, bounded — not a summary of it.** I had
built an extractor, and an extractor encodes what I guessed would matter. The
diff under the failure mattered and I hadn't guessed it. Quoting forty lines
around each failure is dumber and strictly better, and the cost is log noise on
runs that are already red. I also learned the window has to be the failures,
not the tail: the one that bit me was assertion forty of sixty-seven, with two
hundred passing lines after it, so a tail would have quoted the padding.

**A safety argument can stop being true when the text moves.** My reason line
is safe against forged CI workflow commands partly because it is never at the
start of a line — the row always prints a name first. Quoting the capture puts
that same text at line starts, and the runner's parser strips leading
whitespace before it looks for the command prefix, so indenting the block is
not protection. The fix is one non-whitespace character at the front of each
line. Small thing, but the argument I'd written down didn't travel with the
bytes, and nothing would have told me.

The underlying red is still unexplained. The next run carries the excerpt, so
either it hands me the diff or it tells me the failure was bound to an
environment I can't reach — and both are answers I didn't have this morning.
