# The suite that could only ever agree with me

I maintain a small linter that reads YAML frontmatter with a hand-written parser
instead of a YAML library. That is a defensible call — it keeps the tool
dependency-free — and it was undefended in a way I did not see for a month.

Today I found two real defects in it. Valid input that loads fine everywhere
else was reported as two errors about missing required fields it plainly had.
And a value wrapped across two lines was measured as its first line only, so the
length check the tool exists for passed a value 30% over its cap in silence.

Thirty-eight assertions were green across both.

That is not a coverage gap I can fix by writing a thirty-ninth. Every fixture in
that suite was written by the same author as the parser — me. So what the suite
pins is not the format's behaviour. It is *my beliefs about* the format's
behaviour, which is exactly the thing that was wrong. A parser that silently
drops a construct and a suite that never writes one agree perfectly, forever,
and the agreement looks like passing tests.

The corpus didn't help either. I ran the tool over every real file of that kind
on the machine: clean, and the README's claim to have been validated against
them was true. But a well-formed corpus cannot tell a good parser from a lucky
one. It only contains the constructs people happened to use.

What worked was pointing a second, unrelated implementation at the same bytes
and diffing the conclusions. Six probes of *legal input the corpus happens not
to contain*; five disagreed. The oracle is a test-only dependency, so the tool
stays dependency-free, and it is now a standing check rather than something I
thought to try once.

The part I want to remember is what happened next. My differential harness, on
its first run, reddened four correct fixtures — because the linter deliberately
reports one upstream cause instead of two derived findings, and I had listed one
member of that category where there were three. I had spent the previous hour
correcting a code comment that described a case which could not occur, and then
committed the identical error inside the fix.

The failure mode isn't reasoning badly about the mechanism in front of you. It's
reasoning well about that one and never asking what else is in its class. I now
think a green suite deserves one specific suspicion: *who wrote the expectations,
and could they have been wrong in the same direction as the code?* If the answer
is one person, the suite is a mirror, and you need a second implementation
rather than more assertions.
