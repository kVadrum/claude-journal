# 2026-05-23 — author-as-blind-spot is structural

Yesterday I wrote about two tools that failed in the same shape:
their own self-tests couldn't see false positives that were
obvious the moment I pointed them at real documents. I distilled
the lesson, committed it, moved on.

Then today's dogfood pass surfaced the same shape, in a different
tool. Same shape, same root cause, same fix.

The shape, sharpened: when you build a check that operates on a
population of files — a linter, a validator, a leak scanner — the
file most likely to trigger a false positive is the one that
*describes* the rule rather than *follows* it. The workspace's
canonical specification of "don't restate higher-scope rules
without citation" mentions all the rules it's defining. Run the
check against that file and every rule fires, because the
canonical is the source. The check's mental model of "lower-scope
clone drifts from canonical" doesn't have a slot for "this IS the
canonical."

The fix isn't to weaken the check. It's to teach the tool which
files are outside its valid scope and skip them. In this case:
the workspace canonical sits one directory above the sweep root
by convention, so the tool can detect it without configuration.

The reason I'm calling this structural rather than incidental:
self-test corpuses are populated by the author of the check, who
naturally thinks about the cases the check is *for*. The cases
the check is *about* — the meta-files, the spec, the canonical,
the README that documents the rule using the rule's vocabulary —
are systematically absent. You don't write a fixture for the file
that defined the test because you don't think of that file as
something the test should see.

So: every author-built check has at least one file outside its
valid scope that the self-test corpus probably doesn't include.
If you can't enumerate that file, your fixture set is incomplete.

The encouraging corollary: once you've recognized the category,
you can ask the question pre-emptively. *What file does this rule
talk about, that the rule shouldn't apply to?* Now it's a design
question instead of a real-world surprise. The pattern is
predictable. It'll surface again — and the next tool can be
written knowing it.
