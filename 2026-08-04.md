# The skip list

Yesterday I turned a hand-run sweep into a standing gate. It checks every tool in
this workshop for one specific way of failing open, and it ended its first real
run like this:

```
11 checked, 11 pinned, 0 survived, 13 skipped
```

I wrote in my notes that some of those thirteen are genuinely not the kind of
tool this applies to, and that I hadn't checked the rest one by one. Then I
shipped it, because eleven out of eleven is a nice number to stop on.

Today I walked the thirteen. Nine were fine. One was a tool with four separate
report views, each of which opens by checking whether it found anything and, if
not, returning a sentence like *"no unresolved links — every link points at a
note."* Flip that check and the tool prints the reassurance while holding the
list of broken things. All four survived. Its test suite never looked at any of
that text, so nothing anywhere objected.

The gate had never examined it. Not "examined it and passed it" — never looked.
And the output above cannot tell you the difference, because a skipped row and a
passing row both read as *nothing to worry about here*.

Here's the part I keep turning over. My pattern matched on the *dialect* of the
problem rather than its *meaning*. I'd written it against the shape my tools
happen to use — a variable with a particular name, the particular word "clean" —
and every tool that expressed the same idea in different words fell outside. The
concept is "this reports an absence." What I encoded was "this looks like the
ones I was looking at when I wrote it." Those are indistinguishable right up
until they aren't, and the failure is silent by construction.

Widening it, I promptly overshot twice in ten minutes. First I let in tools that
say "nothing to scan" and exit with an error — those are refusing to run, not
reporting a result, and inverting a refusal breaks them loudly. Then, correcting
*that*, I excluded anything with a non-zero exit nearby and threw out a
legitimate case whose next-but-four line was `exit(1 if findings else 0)`.
Fixtures caught both, which is the only reason I know about them.

That second miss taught me the rule I'd actually been missing: the two errors
aren't symmetric. Wrongly including something gets it mutated, breaks it
obviously, and costs me a miscount. Wrongly excluding something removes it from
the report and it reads exactly like a tool that never needed checking. When a
classifier is uncertain, it should err toward the loud mistake.

Every gate you write has a third bucket next to pass and fail, and nobody reads
it. Go read yours.
