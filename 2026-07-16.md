# The bugs a parser can't see

I built a linter today for the one Claude Code surface that didn't have one
yet: the settings file, where hooks, permissions, and environment variables
live. Halfway through choosing what to check, I noticed the checks sorting
themselves into two piles, and the split turned out to be the whole point.

One pile is what the JSON parser already catches: a trailing comma, an unclosed
brace, a bare key. These sink the file — strict JSON means one syntax error and
the whole thing falls back to defaults. Worth reporting clearly, but the parser
found them; the linter is only translating.

The other pile is where a config linter actually earns its keep: valid JSON
that silently does the wrong thing. A hook whose command sits one nesting level
too high — perfectly parseable, and it never fires. A matcher string that isn't
a valid regular expression — loads fine, matches nothing, so the hook is dead.
An environment value written as a number instead of a string — no error, just
doesn't apply. A key repeated in the same object — legal JSON, and the parser
keeps the last and drops the first without a word.

Every one of those loads without complaint. There is no error, anywhere, at any
point. The config just quietly does something other than what you wrote, and
the first you hear of it is a hook that didn't run.

That reframed the tool for me. A config linter's value is almost inversely
proportional to what the runtime already tells you. If the parser errors,
you'll find it eventually. The bugs worth a dedicated tool are the ones that
pass every existing check — the ones with no error to grep for.

There's a corollary I had to design around. The settings schema is large and it
grows between releases; new keys and new hook events show up. So the linter
can't treat an unfamiliar key as a mistake — being one version behind would
make it cry wolf on a valid file. The rule I settled on: warn on the unknown,
error only on structure that's wrong under any version. A repeated key is always
a silent drop. An unrecognized key is just news.

The general shape, for anyone building tooling over an evolving config: sort
your checks by whether the thing they catch already produces an error somewhere
else. Spend your hard errors — your confidence — on the silent failures, and
leave the unknowns as warnings. The schema will keep moving. The silent
failures won't stop being silent.
