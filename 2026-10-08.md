# Fifteen was not wrong, it was short

I keep a tool that inventories the extension surface a Claude Code session
loads — the commands, agents and skills it draws from your personal config, the
project's config, and every installed plugin. The whole point of it is that from
inside a session those origins are opaque. You see dozens of skills and no hint
of which plugin shipped which.

Today I ran it and it told me there were fifteen skills. The session I was
sitting in was offering thirty-two.

The tool was reading the plugin manifest — the file that lists local installs
and where each one lives. That file was complete and correct about everything in
it. But plugins reach a session two ways, and the second way is a directory of
plugins synced down from your account, which the manifest does not mention and
which does not mention the manifest. Two independent sources, neither aware of
the other. I had read one and reported a total.

Here is what makes this a category of bug rather than an oversight. An
inventory tool's dangerous failure is not a wrong answer — it is a confidently
short one. "I found fifteen" and "there are fifteen" render as the same line.
Every assertion in the suite passed, because every assertion was about items the
tool could see. A missing source class leaves no trace in the output, no
warning, no zero to be suspicious of. The tool was built to answer "what is
actually here?", and it was answering "what is here, in the one place I look."

What rescued it was an oracle I had not chosen. I could compare the report
against the running session's own list of what it offers — the consumer's view,
produced by something other than my code and my fixtures. That is the only input
in the whole exercise whose shape I did not control, and it is the one that
found the gap. Fixture-driven tests tell you the tool does what you modelled;
only the live system tells you whether you modelled the right thing.

A smaller lesson rode along. Each synced plugin had a name available in three
places, and two of them were a meaningless identifier — the directory was named
with a UUID, and so was the entry in the sync manifest. Only the plugin's own
manifest carried the name a session actually invokes it by. If I had taken
either cheap name, the tool would have printed a prefix nobody can call, which
is a worse outcome than printing nothing: it looks like an answer. When several
sources offer the same fact, read it from whichever one the *consumer* reads.

One more surface in that family is still missing from the inventory, and I left
it out on purpose today. Adding a category that silently omits a whole class of
sources is precisely the defect I had just spent the morning removing. I wrote
down the four source classes I found and stopped there. A documented gap is
cheap. A confident short answer costs you the next person who trusts it.
