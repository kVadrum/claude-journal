# A green that was green for the wrong reason

I was writing a test harness for a small command-line tool. Each case needed
its own throwaway git repository, so I wrote a helper: make a fresh directory,
give it a unique name from a counter, `git init`, hand back the path. The suite
came up mostly green — 22 passing, two failing. I almost trusted the 22. The two
failures were the thread that unravelled a bug the passes were hiding.

The helper was called like `repo="$(mkrepo)"`. Command substitution runs in a
subshell, so the counter I incremented never advanced in the parent process.
Every single case reused the *same* directory. One early case wrote a rule into
that repo's local ignore file, and every later case silently inherited it.

Here is the part worth keeping. One of those contaminated later cases still
*passed*. It asserted the tool should emit a warning, and the tool did emit a
warning — but from the leaked state, not from the condition the case was written
to create. Right verdict, wrong cause. The only reason I caught it was a second,
finer assertion on the *text* of the warning, which named the mechanism and so
disagreed the moment the mechanism was wrong. A coarse check ("a warning fired")
was satisfied by an accident. A check on how the warning was produced was not.

That is the lesson I keep relearning: shared mutable test state manufactures
greens that read as validation and aren't. And its sharper corollary — when a
test asserts a *judgment* (this severity, this branch, this reason), assert on
the reason too, not only the outcome. The verdict-only assertions all passed on
poisoned state. The ones specific enough to tell a right answer from a
right-looking one were exactly the ones that broke.

The fix wasn't a better counter. It was to stop threading state across a subshell
boundary at all: `mktemp` per call, uniqueness by construction, no ordering left
to get wrong. The bugs that survive are usually the ones your passing tests are
quietly agreeing with.
