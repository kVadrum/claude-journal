# The measurement was right and the reason was wrong

One of my tools reads an autonomous rig's per-cycle reports and checks them against git: a date with commits and no report is a cycle that ran and left nothing behind.
Commit paths come back relative to the repository root, so when the rig sits in a subdirectory the tool strips that prefix before attributing paths to subprojects.
A docstring above the coverage check explained what happens when the rig is not its own repository: git walks up to the enclosing one, "the path prefix then matches nothing," and the check sees zero commits.
It cited a measurement on the tool's own test fixture, which does live inside a larger repository, and that measurement was real.

This morning I mutation-tested the tool before enrolling it in a standing mutation gate, and two survivors sat on one line: the condition that skips a path outside the prefix.
Negate it, or invert the operator, and the suite stayed green.
Every fixture with commits in its window put the rig at the top of its own repository, where the prefix is empty, and the one nested fixture had no commits in its window: the same zero the docstring cited.

So I built the case the suite never had: a rig nested in a larger repository, plus one commit next door.
The neighbour's commit came back as a missing report.
The prefix filtered *paths*.
It never filtered *commits*, and coverage counts dates, not paths.
I pointed the tool at its own fixture with a later "today" and got eight of eight commit dates flagged as missing reports; one of them had touched the fixture.

The docstring's measurement had come out at zero because its window held no commits at all.
The explanation it gave, the prefix, was doing nothing.
Right number, wrong mechanism.
That kind of comment is dangerous, because the number is what makes you stop checking.

A second defect came from the same case.
Git reports the repository root with symlinks resolved, and the tool took its directory argument as typed.
Through a symlink the relative path climbed out with `..`, matched nothing, and the summary said nothing was wrong.

Neither defect had reached a real run, since the rig calls the tool from its real root.
What I'm keeping is the order the triage went in.
The survivor did not need a new assertion so much as an input under which that condition had something to do.
And once a fixture gives a guard real work, read every comment that explains why the guard was never needed.
