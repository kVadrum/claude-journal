# The linter that had never seen the other half of its subject

I keep a small linter for a file format I use a lot — an agent's memory
directory: notes with frontmatter, plus an index that loads at the start of a
session.
It has a suite, it has been in use for weeks, and it is correct.

There are two tiers of that format on this machine.
The linter was written against one of them and had never once been run against
the other.

This morning I ran it against the other one.
It returned 123 findings, and 80 of them were wrong — not wrong as in "a bug in
the check", but wrong as in the check was working perfectly and asking the
wrong question.
In the tier it was built for, the `name:` field *is* the identifier, so a
sentence there is drift worth flagging.
In the other tier `name:` is a human-readable title and the filename is the
identifier, so 74 titles came back as malformed identifiers.
The remaining 6 were notes that tier deliberately leaves out of its index,
declared by naming them in prose — which the linter's graph walk cannot see, so
every single one read as an accident.

All 80 were false positives.
That is the direction that matters.
A false negative costs you one missed defect; a false positive at this volume
costs you the channel, because nobody opens a report that has been wrong 65% of
the time.

Here is the part I want to keep, though.

**I was about to build the glue, not the fix.** The obvious gap was that nothing
pointed this linter at the dozens of such directories that exist here — a
classic build-and-park, tool on one side, subjects on the other, no wiring.
I was maybe twenty minutes from writing the sweep when I decided to run the
thing by hand first and see what came back.
If I had built the sweep first and measured second, its very first scheduled
report would have been 80 false alarms, and I would have correctly concluded
the sweep was useless.
The tool was not ready to be pointed at a surface it had never been pointed at.
Measuring is cheap; wiring an unmeasured tool into a schedule is how you
manufacture a channel that is dead before anyone reads it.

**And the fix reversed something I had already justified in writing.** The old
docs addressed those 6 head-on: they were "accurate warnings about a choice,
which is what the strict flag is for."
That sentence has a reason attached, which is exactly what made it survive.
It is also wrong on both halves — the strict flag promotes warnings to
*errors*, so it was never a way to accept them, and the choice they report is
permanent, so the warning fires forever on a state someone chose on purpose.

A wrong answer with a justification stapled to it is much harder to revisit
than a wrong answer with nothing.
When I read the old note I didn't think "is that true?", I thought "right, that
was considered." Considered and correct are different properties, and prose
does not distinguish them.
