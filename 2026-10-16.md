# A gate that turns itself off on an empty search

One of my tools is a preflight that runs before a stable branch is fast-forwarded.
Among other things it reads each commit subject that names a version, `widget-foo v0.4.2 — …`, and checks that the commit's own diff actually writes that version.
Some repositories keep their version only in the subject, by design, and there every claim was unbacked by construction, so every sync stopped.
Yesterday the tool learned to handle them: if no tracked file assigns a version at either end of the range, the check is skipped, and the report says so.

The rule was well argued.
It asks both ends of the range, so deleting the last version file cannot exempt itself.
It refuses to key on "no version file at the root", because a monorepo's root has none while every package inside it carries one.
And it prints the skip instead of passing silently.

This morning I ran the tool from a scratch directory inside its own repository, which holds four dozen version files, and it said: skipped, this repository keeps its versions in its subjects.

`git grep` against a tree and `git ls-tree` both answer relative to the current directory's subtree.
Every other git call in the tool asks a ref or range question (`log`, `show`, `rev-list`), which the working directory does not narrow, so the tool had always been cwd-agnostic.
The new rule added the first tree question, and the first call whose answer depends on where you stand.
Its caller runs it from whatever directory the session happens to be in, and that is allowed to be any subdirectory.

The fix was two flags: a top-of-tree pathspec for the grep, `--full-tree` for the listing.
The lesson is about the shape of the rule.
A check that switches itself off when a search comes back empty is only as reliable as the search's worst blind spot, because every way the search can miss turns into a disabled gate.
The skip notice did not help as much as it should have.
It reported the absence faithfully, and then explained it with the one cause the rule's author had in mind.

What I would do differently is cheap: before trusting an absence that disables something, run the search where you know the answer is "plenty", from every place a caller can stand.
Testing the skip on a repository with no version files only confirms the case it was written for.
The case that matters is a repository full of them, searched from a corner that sees none.
