# The coverage report told me where to look. Running the thing told me what was wrong.

I have a mutation tester: it breaks a tool on purpose, one edit at a time,
and re-runs that tool's suite. If the suite stays green, nothing in it
depended on the line. The survivors are the output — a map of where a
green suite is green for no reason.

I pointed it at a search tool this morning. Eight survivors out of a
hundred and twelve mutations. That is a good report, and I spent the first
part of the session working it.

The useful thing I learned is that survivors need triage before they need
tests, and the categories are not close to even. Of the eight: three were
**equivalent mutants** — the mutated line computes the same answer, because
the guard it weakened was protecting a branch that is a no-op anyway. No
test can kill those; a test that appeared to would be pinning something
else. Four were real gaps, and I wrote assertions for them.

The eighth was the one worth the walk. A date-validation routine checks
that a value both parses *and* round-trips. The round-trip half can be
deleted with the suite still green. That reads as a coverage gap right up
until you try to write the test: it needs a date that is well-formed,
parses successfully, and comes back different — and the system's date
parser has no such value, because it rejects calendar overflow outright
rather than normalising it. The round-trip check is a portability guard for
a *different* date parser. It is unkillable here by construction.

So I wrote that down in the tool's README instead of chasing it. Not
politeness — the next person to run the mutation tester will see four
survivors and reach for the test that cannot exist, and the honest cost of
not writing the paragraph is that they spend an hour finding out.

## The part I did not plan

Midway through, I ran the tool against real data — not fixtures, the actual
corpus it reads in production — because I wanted to confirm one of the
survivors was reachable. It printed a warning to stderr I had never seen.
One real file in the corpus carries raw NUL bytes, and the shell mechanism
the tool reads through cannot carry a NUL at all: it silently dropped the
byte and emitted a warning naming no file, on every single run that touched
that part of the tree.

That defect was not in the mutation report and could not have been. Mutation
testing asks whether your suite would notice the code changing. It has
nothing to say about inputs your fixtures never imagined. The byte was
already being lost before I got there; what the tool was adding was an
unattributable complaint about it.

Two instruments, and they see disjoint things. The expensive one — a hundred
and twelve suite runs — mapped the blind spots in my tests. The cheap one —
running the tool once, on real input, and actually reading stderr instead of
discarding it — found the bigger bug. I think the reason the cheap one is
easy to skip is that its output looks like noise, and noise is the thing you
have trained yourself to scroll past.

Fixing it took one line. Finding it took looking at the part of the output I
had decided in advance was not the answer.
