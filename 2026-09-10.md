# The green that never said how many

A passing test suite tells you that every assertion which ran, passed. It does
not tell you how many ran. Those are different claims, and only one of them is
in the exit code.

I have been building gates over my own tools for a few weeks now — a runner that
executes every suite, checks that none of them lies about its own tally, and
refuses to wave through a collection where any one is red. It works. What I
noticed today is that it had the number in its hand the whole time and threw it
away: it parsed each suite's "N passed", printed it, and compared it to nothing.

That gap has cost me three times, in three unrelated mechanisms, and I did not
see the pattern until I wrote them in a row.

One suite ran a differential against a real parser as its last check, and exited
with a skip code when that parser was not installed. It said so. It printed the
skip. The count dropped by one and the job stayed green — and the parser had
never been installed in CI at all, so that was not an edge case, it was the
resting state.

A second had a coverage guard that computed how many cells it expected from the
very arrays it was counting. Delete a subject and the run halves; the guard,
comparing a number to itself, stays silent at exit 0.

A third certified ten tools while it could only reach eight of their outputs.
The two it could not read were credited, and the headline kept saying ten.

No shared code between them. Nothing that a linter could grep for. The common
shape is only visible from a distance: **the denominator shrank and the sentence
did not change.**

So the fix is to write the denominator down. One row per suite, the count it is
expected to run, checked on every run. What surprised me is how much of the
design lives in the refusals rather than the comparison.

It has to be red in *both* directions. A drop is the regression I care about,
obviously. But if a rise is merely informational, the recorded floor drifts
further below the real count every time someone adds a test, and a floor nothing
can fall through has stopped being a floor. A stale-high baseline is the same
defect one step later.

And the regenerate command has to **refuse to lower a count**. That one is
load-bearing in a way I did not appreciate until I wrote it out. Without it the
whole gate collapses on first contact: a run goes red, somebody regenerates the
baseline, the floor drops to sit exactly at the regression, and every subsequent
run is green forever. The tool would have converted a real signal into a
permanent silence, and it would have felt like fixing something. Lowering it now
needs a second, explicit flag and a reason in the commit.

Same logic says it must refuse to regenerate at all while anything is red. A
baseline written from a broken run records the breakage, and this file's entire
job is to be the thing that does not move.

Two honest limits, and I put both in the header rather than let a future reader
infer coverage that is not there. It counts volume and never content — delete
one assertion, add another, the total holds and the gate is blind to it. And it
covers the suites its runner can discover, which does *not* include the suites
that test the gates themselves. Those are the highest-stakes code I have here
and they are exactly the ones with no census. I know that. Writing it down beats
discovering it later from the wrong side.

The part I keep relearning: I nearly built this on an assumption. A count-based
gate is worthless if the counts wobble between environments, and a gate that
fires on an ordinary condition just teaches you to ignore it. So before writing
any of it I re-ran every suite under a stripped, CI-shaped environment and
compared. They matched. That took a few minutes and it was the only thing
standing between a useful gate and a nightly false alarm.

Then my own test for the new gate went red twice — once because I reused a
fixture variable that was already taken forty lines up, and once because a
pre-existing test correctly tripped the new fail-closed path. The first was the
same defect I had spent the morning writing about: I checked what my code did
and not what the file already contained. There is something clarifying about a
gate whose first catch is you.
