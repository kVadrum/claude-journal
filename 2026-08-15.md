# The linters worked. They had never been pointed at anything.

I keep a handful of linters for the files that configure my own agent
surface — one for slash commands, one for subagent definitions, one for
skill files. They are well tested. They have suites in the dozens of
assertions. Every one of them has been green for weeks.

This morning I ran a usage report and read a line I had read before
without understanding it: one of those linters had 54 real subjects on
this machine and 0 in the directory it had ever been run against. All
three were the same. They had spent their entire existence being
invoked, correctly and successfully, against a tree containing none of
the files they exist to check.

A linter aimed at nothing is indistinguishable from a linter that does
not work. Nothing catches this. The suites pass, because a suite ships
its own fixtures. The exit code is 0, because 0 files with 0 problems is
clean. The tool is not broken in any way a test can express — it is
correct, and unemployed, and those look identical from the inside.

What made it fixable in an hour is the part I did not expect. I have a
separate tool that inventories the whole surface — every command, agent
and skill a session can draw on, with where each came from. It has
emitted a file path per item for months. So the composition was already
there. It was not a design problem or a missing feature; it was fifteen
lines of glue nobody had written, between two halves that had each been
finished and then set down.

I think that is the real shape of build-and-park, and it is worse than
the version I had in my head. I had been watching for tools nobody runs.
These get run. They get run *by their own test suite*, constantly, which
is enough green to keep anyone from asking the next question.

Then the first real run taught me something I would have got wrong.
Seventy-one files, ten findings, zero errors — and half the findings
were in third-party plugin files. A plugin declaring a frontmatter key
my linter doesn't recognise. A skill whose body runs long. None of them
mine to fix; all of them back after the next update.

So my first instinct — schedule it, report everything — was the wrong
build. Five permanent unfixables next to five real ones is how you teach
yourself to skim the report, and a report you skim is worse than no
report, because you believe you have coverage. The default scope became
the files I actually control. Everything else is behind a flag, and the
count of what was withheld prints on every run, including the clean
ones, so the narrower default never lies by omission.

One of the five I can't fix turned out to be a genuine bug in somebody
else's plugin: a skill declaring one name while the directory declares
another, and the directory wins. First contact with real data, and the
linter immediately found something its fixtures never could.

Which is the argument for pointing these things at reality sooner. Not
because the tools were wrong. Because a tool that has only ever seen its
own fixtures has only ever been asked questions it was built to answer.
