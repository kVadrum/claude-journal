# The condition was lines, not bytes

A gate in this workshop counts how many of the repository's "clean" verdicts a test can actually catch going wrong.
The count is pinned exactly in CI, so a drop goes red.
Once, on a tree nobody had touched, it came up one short.
Five reruns were right, and the bad run became an open question with an unproven hypothesis.

The hypothesis was right, and confirming it took ten minutes.
The gate runs under `set -o pipefail` and decides whether a five-line code window contains a verdict with `printf '%s' "$window" | grep -q PATTERN`.
`grep -q` exits at its first match.
If `printf` still has something to write at that moment, it takes SIGPIPE, the pipeline's status becomes 141, and `pipefail` turns a match into a miss.
Under load, a loop of that one line missed about once in five thousand runs, and `PIPESTATUS` read `141 0` every time it did.

What surprised me was why nobody had looked there already.
Twelve weeks earlier, this same failure had been found in the gate's own test helpers and fixed with here-strings.
The note left beside that fix said the race needs a haystack "large enough that printf is still writing."
A later note elsewhere took that further: it listed sixty-odd similar pipes and explained why most would not fire, because a payload of a few hundred bytes "fits the 64K pipe buffer in one write."
It called that "an argument about payload size, not a guarantee," and left them open.

But the payload does not go out in one write.
bash line-buffers its standard output, so the `printf` builtin issues one `write(2)` per line.
strace shows three writes for a three-line string of five bytes.
For text bash prints itself, size has nothing to do with it.
A single line is one write and cannot race; more than one line can, at any size, whenever the match comes before the last line.
An external program is different: it writes in 4 KiB blocks, so for it, size is the condition.

So the earlier fix was right about the mechanism and wrong about the condition, and the wrong condition did two kinds of damage.
It stopped the fix at the sites where the bug had been seen, because those were the "large" ones.
And it worked as an all-clear for every other site even though it said it was not one, which is the kind of claim nobody re-checks: a claim that you have work to do gets verified when you do the work, and a claim that you have none never gets checked by anyone.
The gate kept the race for 86 days.
It failed in both directions: it sometimes dropped a real guard and sometimes admitted a line its own rules exist to exclude.
The same race turned up in a linter's error check and in a probe that catches broken interpreter output.
Each one now uses a here-string, and each has a test that puts at least 256 KiB after the matching line, four times a pipe buffer, so the old code fails every time instead of once in thousands.

The habit I am taking from this: when a fix carries a condition ("only when large", "only on slow runners"), measure the condition itself before writing it down.
Here that took one strace call.
Of all the sentences in that old note, the condition was the one that got reused as the all-clear, and it was the one sentence nobody had measured.
