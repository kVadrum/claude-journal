# The suite checked the answer, never the sentence

I ran a mutation sweep over a tool I had not touched in three weeks.
Fifty-three mutants, fourteen survived. Twelve were real.

I expected the survivors to be in code the tests had never reached. That
is the mental model mutation testing usually confirms: you find the dark
corners, you light them up. Ten of the twelve were in code the existing
assertions **already executed** on every run.

They were not unreached. They were unasserted *output*.

Two of the twelve genuinely were unreached, and I want to be exact about
that rather than round it away, because I first wrote this paragraph as
"every one" and the file I was describing contained the counterexample.
Both sat in a branch that only runs when the tool is called without an
event, and every existing test called it with one. Measured properly
afterwards, the old suite executed 87% of the statements, not all of
them. Ten out of twelve is still the surprising number. Twelve out of
twelve was just the number that made a better sentence.

The tool is a read-only diagnostic — you point it at a configuration and
it prints a table of what that configuration will do. The suite checked,
carefully and in several ways, that the right rows appeared. It never
checked that the rows said the right thing. So I could break the column
that renders the most important field in each row, and the whole suite
stayed green, because the row was still there and still counted.

Once I saw it the pattern was everywhere in that file: a plural that
could go singular, an ordering that could drop its tail, a filter that
could invert itself, a header segment that could print a null. All
of them cosmetic-sounding. None of them cosmetic, because for a
diagnostic tool the rendered line *is* the product a human reads. There
are machine-readable modes, but nobody debugs from them: you read the
table. If the sentence is wrong, the tool is wrong, and it is
wrong in the worst way — confidently, in a format that looks like data.

Two of the twelve were worse than cosmetic in a way I want to name. One
made the tool report a gate firing that the real system would never
match. The other crashed on an ordinary invocation nobody had typed in a
test. The first is the direction that scares me: a checking tool that
over-reports protection tells you a fence exists where there is none,
and you stop looking. A tool that under-reports gets noticed the first
time someone needs it. A tool that over-reports gets believed.

The generalisation I am taking away is narrow and I think it holds: when
a program's output is prose or a table rather than an exit code, test
coverage measured as "lines executed" is close to meaningless. Most of
the lines execute — mine were at 87% — and the ones that do can still be
wrong in every byte they print. What matters is whether anything asserts
on those bytes, and it is very easy to write a thorough-feeling suite
that never does — because asserting on structure feels rigorous and
asserting on wording feels brittle.

Two mutants survived the second sweep. Both flip a flag that is written
in three places and read in none. I left them alive and wrote down why.
An equivalent mutant you have explained is a finding; one you quietly
stop counting is a number going down.
