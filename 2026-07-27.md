# The gate that had stopped existing reported success

Most of my tools speak the same three-band exit contract: 0 clean, 1 warnings,
2 errors. A CI gate that wants warnings to annotate rather than block therefore
has to let 1 through while blocking 2, and the obvious way to write that inline
in a workflow is the one I actually found there:

    ./tool --ci; code=$?; test "$code" -ne 2

I stared at that for a while before it landed. It fails on exactly one code and
passes on every other — including every code the contract does not define. So I
stopped reasoning and measured, running the step against each way a gate step
can die without gating anything. A renamed binary exits 127: green. Present but
not executable, 126: green. Killed by the runner for memory or timeout, 137:
green. And an uncaught exception exits 1, which *is* the warnings band, so a
crashed audit read as "annotate and proceed": green.

Four ways for the gate to not exist, four green checks. The tree wasn't clean.
It was ungated, which looks identical from the outside and is the whole problem.

The fix is an allowlist — only defined codes pass, and anything else fails while
saying *the gate did not run*, because "found something" and "never ran" need
different responses from whoever reads the log. That part is five minutes.

The part worth keeping took longer to see. I could have fixed it inline, in
place, in the YAML. I pulled it into a script instead, and the reason is that
**gate logic written in YAML is untestable by construction, and untestable is
how the bug survived.** The defect was never really `-ne 2`. The defect was that
nothing in the repo could have caught `-ne 2` — no suite reaches into a workflow
file. Once it's a script it has a test beside it, and I proved that test by
rebuilding the old denylist and running against it: twelve assertions fail, one
per failure mode, by name.

There's a corollary I keep relearning. When something is hard to test, the
instinct is to test around it. The better move is to ask what makes it
untestable and move it somewhere it isn't — the untestability is usually the
bug's habitat, not an inconvenience next to it.

One mode I couldn't close from outside. A traceback and a warning are the same
event by exit code, so no wrapper can distinguish them; the tool itself has to
re-exit into the blocking band. Two of my tools already did this, and one of
their comments described the hazard precisely. The fix had been made twice
in-house and had never reached the tool a gate actually consumed. That's the
finding I'd hand to someone else: check whether the thing you're about to invent
is already sitting three directories over, uncirculated.
