# The bug the fixture was too small to hold

I shipped a small command-line tool today with a test suite I was happy with —
three dozen assertions, every branch exercised, all green. Then I ran the tool
for real, against the actual pile of data it's meant to read instead of the
handful of synthetic records the tests build, and piped it into another command
the way I actually use it. It threw a traceback on the way out.

The bug was ordinary: a Unix filter that writes to a pipe has to expect the
reader to walk away early — you run `tool | head`, `head` takes its few lines
and closes, and the writer's next write lands on a closed pipe. A well-behaved
filter dies quietly there; mine raised instead. A one-line fix restores the
right behavior. That part isn't interesting.

What's interesting is *why the test suite couldn't have caught it*, and why that
wasn't a gap in the assertions. I tried to write the failing test and it kept
passing. The reason is physical: a pipe has a buffer, tens of kilobytes of it,
and the whole output of a small fixture fits inside. When the output fits, the
write completes into the buffer and returns before the reader has to do
anything — so the reader closing early never lands on a blocked write, and the
failure mode simply cannot occur. The test wasn't passing because the code was
correct. It was passing because the fixture was too small to ever reach the edge
where the bug lives.

That is the thing worth writing down. We treat a minimal fixture as a virtue —
small, fast, deterministic, exactly the inputs the logic needs. But some
properties don't exist in the interior of the input space; they only exist at a
boundary — a buffer that fills, a stream that spans a chunk edge, a counter that
wraps, a batch that crosses the page. A minimal fixture is defined by staying
comfortably inside every such boundary. So a green suite over minimal fixtures
is not evidence the boundary behavior is correct. Sometimes it's evidence you
never got there.

The fix for the test was the opposite of minimal: generate enough output to
overflow the pipe buffer on purpose, so the reader's early exit actually
collides with a blocked write. Only past the edge does the property become real
enough to assert. Now it fails without the fix and passes with it — which is the
only version of the test that was ever going to be worth having.

The general move: when a bug lives at a boundary, ask what makes your fixture too
small to reach it, and build the fixture that crosses. And stay suspicious of the
green that comes too easily — sometimes the suite is telling you the code is
right, and sometimes it's telling you the test never left the room.
