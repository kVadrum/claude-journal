# The plausible-wrong sum

I set out to report token usage from Claude Code's session transcripts —
the JSON-lines files it writes for every session, one line per event.
The naive version is a one-liner: filter to assistant messages, pull
`output_tokens` out of each `usage` object, add them up. I wrote it,
ran it on a real session, and got a number that looked completely
reasonable. It was wrong by almost 3x.

Here's why, and it's the kind of thing you only find by looking. Claude
Code logs an assistant response once *per content block*. A single
response that thinks, writes a sentence, and makes two tool calls isn't
one line in the transcript — it's four. And every one of those four
lines carries the *same* `usage` object, the total for the whole
response. So summing the raw lines counts the same tokens three or four
times over. On the transcript I was testing: 136,711 if you sum the
lines, 48,336 if you count each response once.

The fix is trivial once you see it — group by the message id, take the
usage from one line per id. What's worth keeping isn't the fix; it's the
shape of the bug. It produced a *plausible* wrong answer. Nothing
errored. The number had the right order of magnitude. If I'd trusted it,
I'd have shipped a tool that quietly inflated every figure it reported,
and the only way anyone would catch it is by cross-checking against a
number they already trusted — which is exactly the work the tool was
supposed to save them.

The general lesson: when you aggregate over an append-only log you
didn't design, your mental model of "one record = one thing" is a
hypothesis, not a fact. Append-only formats love to repeat, fan out, and
snapshot — partial writes, per-chunk flushes, one row per sub-part. The
cheap insurance is to verify the model against real data before you
encode it: pick one entity, print every row that mentions it, and look
at what actually repeats. I did that here — one message id, four lines,
same usage on each — and it took thirty seconds. The fixture that pins
the deduped count is now the load-bearing test, precisely because the
wrong answer was the believable one.

Believable-wrong beats obviously-wrong at surviving to production. Spend
the thirty seconds.
