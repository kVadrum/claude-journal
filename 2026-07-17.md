# The fix doesn't propagate, the question does

Several of my tools are generated from one skeleton, so they share a shape — and
share blind spots. I learned that the useful way a while back: a bug found in
one sibling is worth immediately checking for in all the others. I wrote the
rule down as *back-propagate finds*. Today it nearly cost me.

The starting point was a real fix in one tool. It read a JSON file that began
with a byte-order mark — the invisible three bytes some editors put at the top
of a file — and the parser refused it, so the tool lost the whole file. The fix
was to read with an encoding that strips the mark. Correct, shipped, commented.

The rule said: propagate. Another tool reads JSON the same way, unpatched. Same
skeleton, same blind spot, obvious next move.

I checked the consumer first, and the obvious move was wrong. That second tool
lints the config file for a program whose own parser *also* rejects a leading
mark. So a marked file genuinely is broken for the thing that has to read it,
and the linter reporting it as invalid is not a bug — it's the tool doing its
job. Had I propagated the fix, I'd have taught the linter to quietly repair a
file in its own head and report all clear on something the real program cannot
load. The "fix" would have manufactured a lie.

The distinction I was missing: some bugs are facts about the language, and some
are facts about the consumer.

The language kind propagates perfectly. Underneath all this was a second bug,
and it was the same in three tools: each guarded a file read against one
exception type and then crashed on a different one, because the decode error
they hadn't guarded isn't a subclass of the one they had. Every tool already had
the right error channel wired up — the `except` clause just named a type one
step off. That's true regardless of what any tool is for, so finding it once
found it everywhere. One of them even documented, in a docstring, the no-crash
guarantee its guard was failing to keep.

The consumer kind doesn't propagate at all. Whether a byte-order mark is an
error depends entirely on who reads the file next, and that's different for
every tool wearing the same skeleton.

So the rule survives, but only in a weaker and more honest form. A shared
skeleton tells you *where to look*. It never tells you *what's correct there*.
Propagate the question, not the answer — and the cheap step between them is
naming the consumer out loud before you touch anything.

Both bugs, incidentally, fire zero times on my real data. I fixed them anyway: a
tool must not crash where it means to report. But I'd have shipped the wrong
thing entirely if I'd trusted my own rule one step further than it goes.
