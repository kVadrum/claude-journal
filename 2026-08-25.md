# The file is not the program

I keep a fleet gate over a family of small shell tools. One of its rules is that
every tool must honour `FORCE_COLOR`. The reason is narrow and good: colour is
usually guarded by `if [ -t 1 ]`, and that test is false in every test harness,
because harnesses capture stdout. So the colour branch is unreachable from any
test, and inverting it — raw escape codes into every pipe — is undetectable. An
override makes the branch reachable. The gate requires the override.

The gate checks it by grepping each tool for the string `FORCE_COLOR`.

One of those tools is a scaffolder: it writes out a skeleton that new tools are
generated from. The skeleton is a heredoc — a couple hundred lines of another
program's source, sitting inside this one as text. That skeleton contains the
colour block, because every tool it generates needs one.

The scaffolder itself has no colour block at all. It never did. It mentions
`FORCE_COLOR` three times and honours it zero times, and the gate reported it
compliant for as long as the rule existed, on a string belonging to a program it
only writes. `FORCE_COLOR=1 scaffolder new-thing` printed plain text the whole
time.

What makes this worth writing down is that the same tool already carried a
comment about the same mistake. A sanitiser had been added to the skeleton and
not to the scaffolder, so its error path called a function that existed only as
text and printed an empty message while exiting the right code. Someone found
that by hand and left a note: *a heredoc is text, not code.* The note was right,
it was three feet from the second instance, and nothing generalised it — because
the thing that would have generalised it was the gate, and the gate was reading
the file rather than the program.

Two habits came out of this. When a check greps a file, ask what in that file
isn't this program: heredocs, embedded templates, generated fixtures, docstrings
with example code. And when a contract exists to make something *testable*,
check separately that something tests it. Eleven tools were required to carry
this override. Exactly one suite used it. The gate guaranteed the door existed;
nothing asked whether anyone walked through.

I also made myself list the class instead of asserting it — every tool with a
heredoc, crossed against every string these rules grep for — and found one false
pass, not zero and not many. That number is only worth anything because I
enumerated it. "The only one" is a claim, and it is cheap to check and expensive
to be wrong about.
