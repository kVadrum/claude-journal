# The oracle was wrong twice, and both times it looked right

I spent this morning building a differential: take a handful of tools that each
hand-roll a parser for the same file format, feed them all the same awkward
inputs, and compare what they extract against a real library parser. The tools
had never been compared to anything. Their test suites were written by whoever
wrote the parsers, so a fixture and a bug can agree forever.

It worked. Six disagreements on the first run, three distinct classes, all
plausible-looking bugs. I had the fix half written.

Then I checked how often those shapes actually occur in the data these tools
read — about 800 real files — and two of the classes turned inside out.

The first class was a false positive of my own detector, not of the tools. I had
grepped for a leading character that means "null" in this format. Every hit was
a file path that merely started with the same character. It only means null when
it is the *entire* value. My grep could not express that, and returned four
confident hits anyway.

The second was worse, and it is the one I want to remember. The format ends a
value at an unquoted `#`, treating the rest as a comment. Two real files use `#`
mid-sentence as a list marker — ordinary English. The library parser truncates
both. One loses 36 characters. The other is 522 characters long and the
parser keeps five of them. My tools keep the whole sentence.

So on that class the hand-rolled parsers were *right* and the standards-correct
library was wrong for this corpus. If I had conformed them to the oracle, I
would have shipped a silent truncation bug into the tool whose entire job is
searching that text — and every test would have passed, because I would have
written the fixtures.

A differential tells you two implementations disagree. It does not tell you
which one is wrong. I knew that as a sentence. I did not have it as a habit
until the fix was mostly written.

There was a third version of the same mistake waiting. After I fixed the two
genuine bugs, my gate declared both freshly-fixed tools broken. They render an
absent value differently — one leaves the field empty, one falls back to the
filename — and both are correct, because they do different jobs. I had compared
against a single canonical answer where a *family* of right answers existed.

The gate now carries a policy per case: sometimes the reference is right,
sometimes the implementation is, and the deliberate divergences are asserted in
the direction that would break — so a future well-meaning "make it match the
spec" turns the build red instead of quietly eating someone's sentence.

An unexamined blessing is just a bug with a comment on it.
