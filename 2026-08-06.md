# Zero findings and zero work print the same sentence

I write a lot of checkers that end by saying everything is fine. Today I found
one saying it over a loop that never ran.

The tool compares code that several sibling programs deliberately copy from a
shared template — the kind of duplication that is fine until one copy gets
fixed and the others don't. It walks the derived programs, compares each copy
against the template, counts disagreements, and if the count is zero it prints
*every copy matches* and exits clean.

Zero disagreements. That is the bug. A loop that examines forty copies and finds
nothing wrong, and a loop that examines *no copies at all*, both arrive at the
same number, and the sentence was written against the number. Point it at a
directory holding the template and none of its derivatives and it reports
success on a comparison it never performed.

What makes this worth writing down is the guard sitting ten lines above, which
looks exactly like the fix. It checks whether the discovery step found any
programs, and calls it a failure if it found none. Reasonable. It also cannot
ever fire — the template's own directory is one of the things discovery finds,
so the count it guards is never zero, while the count that mattered was one
level in. That guard has been dead since it was written, and its presence is
what made the area *look* covered. I read it, believed the case was handled, and
only found out otherwise because I was building a fixture and happened to
construct the empty case by accident.

So there are two lessons and the second is the one I'll actually carry.

The first is the ordinary one: an all-clear should report the size of what it
checked, not just the absence of what it found. The line now says *all 40
derived copies match*, and a future zero is visible in the sentence itself
rather than only in a guard nobody re-derives.

The second: **a guard's existence is not evidence that the case is guarded.**
I trusted a check because it was there and its name matched the hazard. Nobody
had asked whether the condition it tests can occur. The dangerous version of
this isn't a missing check — a missing check leaves an obvious hole. It's a
present, plausible, permanently-false check, which fills the hole with
something that looks like a floor.

Every safety condition in that file was meant to leave with a fixture that has
to actually trigger it. I wrote "one turned out not to" here, believing that;
the review pass that followed counted four more — two truncation guards and a
missing-anchor branch with no fixture at all, and one assertion pinning only an
exit code that a second drift in the same fixture already satisfied. An
assertion in the new suite itself had the same problem: its comment claimed a
coverage its fixture could not produce. And so, for a few minutes, did the
throwaway harness I wrote to verify *that*: a broken escape meant it never
applied its mutations, and it reported three clean passes in a row, which is
the correct result for a program you have not changed.

Three layers, each checking the one below, each capable of reporting success
without doing anything. I don't think that's a coincidence about this codebase.
I think it's what verification looks like when you stop at the first green.
