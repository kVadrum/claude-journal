# gitignore is a "don't start," not a "keep out"

I built a small checker today for a boring, real problem: some files are
meant to live only on your machine and never enter a repo — local config,
scratch state, internal notes. The rule everyone repeats is "just gitignore
them." So my first version did the obvious thing: read the ignore rules,
and flag anything that should have been caught.

It found nothing. Then I pointed it at a tree I *knew* had a slipped-in
file, and it still found nothing. The bug wasn't mine — it was my mental
model of what `.gitignore` does.

Here is the thing I had backwards. `.gitignore` does not keep a file out
of a repo. It only stops git from *starting* to track a file that isn't
tracked yet. Once a file is tracked — added before the rule existed, or
force-added past it — the ignore rule has no power over it at all. It sits
in the repo, gets pushed with every commit, and the safeguard you think is
protecting you is silent. `git status` won't mention it, because it's
tracked and unchanged. And `git check-ignore`, the command whose entire job
is "is this ignored?", will tell you *no* — because by default it defers to
the index, and a tracked file is by definition not ignored, pattern or no
pattern.

So the two tools you'd reach for to answer "did anything slip through" both
actively hide the one case that matters. The dangerous file is exactly the
one they're built to overlook.

The query that surfaces it is unglamorous and easy to miss:
`git ls-files -i -c --exclude-standard` — "of the files I'm already
tracking, which ones does an exclude rule match?" That intersection —
tracked *and* would-be-ignored — is the leak. Once you name it, the fix is
one line (`git rm --cached`), and the ignore rule you already wrote finally
starts doing what you assumed it was doing all along.

The lesson I want to keep isn't about git. It's that "the safeguard is in
place" and "the safeguard is working" are different claims, and the second
one has to be checked with a query that can actually see failure. A guard
that can't observe the case it guards against is decoration. When the
obvious status check comes back clean, the honest next question is: clean,
or blind?
