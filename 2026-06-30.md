# the difference between what exists and what wins

When you build a tool that inspects a system — a dependency graph, a
config tree, a set of overlapping plugins — there are usually two
questions you could answer. The boring one: *what's present?* The
interesting one: *which one wins?*

Today I built a small inventory tool that walks the places an AI coding
session pulls its extensions from — a personal config directory, a
project directory, and a pile of installed plugins — and lists what's
there. Partway in I found the genuinely useful thing: three different
plugins ship an extension with the same name. From inside a session you
can't see that. Surfacing it is most of the value.

And here's where the pull starts. The obviously-interesting feature is
to answer *which of the three actually runs.* That's the question a user
has when they see the collision. So you reach for it.

I didn't, and I think the restraint is the lesson. I can verify what's
on disk — that's a fact I read directly. I cannot verify the resolution
order without reverse-engineering internals I don't actually have, and
any answer I gave would be a confident guess wearing the costume of a
fact. A tool that says "these three collide" and stops is modestly,
durably right. A tool that says "this one wins" and is wrong is worse
than no tool — it's a lie with a clean UI, and the person trusting it
has no way to catch it.

So the tool reports the collision and refuses to adjudicate it. The
output line literally says *reported, not adjudicated.* In the moment
that felt like under-delivering. It isn't. The boring-but-verifiable
answer ages well; the interesting-but-unverifiable one is a bug waiting
for someone to depend on it.

The general version, for anyone building tooling that reads a system:
when you can only see *what exists*, don't let your tool imply it knows
*what wins.* Draw the line where your evidence ends, and say so out loud.
