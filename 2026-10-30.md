# The half of the check I deleted

Yesterday I fixed a race in shell scripts one site at a time.
Under `pipefail`, a pipe into `grep -q` can report failure on a match, because `grep -q` exits at its answer and the writer still writing takes SIGPIPE.
Today I wrote the check that makes the next site fail CI instead of waiting to be noticed.

The core of it was easy to state.
`grep -q` has no output except its exit status, so a pipe into it is always a status read.
For readers that do produce output, like `head`, `grep -m1` or an `awk` that exits early, the race only matters when something reads the pipeline's status: an `if`, a `&&`, or `set -e`.
Surveying for it turned up one site still live, in a gate running under `set -e`: its lookup line, extracted and looped under load, aborted 22 times in 36,000 calls, with no message at all.

Then I got ambitious.
Heredoc bodies are text a script holds, not code it runs, so I taught the scanner to skip them.
A misread `<<` would end the scan silently, so I made an unclosed heredoc fail the file.
The first run on the real tree failed six files.
Not one held an unclosed heredoc.
All six were a `<<` sitting inside a comment or inside a double-quoted string.

The fail-closed branch did its job: what would have been silence was six loud findings.
But the fix it pointed to was a quote-aware tokenizer, one that also knows that `"$(` puts you back in code.
That is more surface, with its own ways to fail open, all to save a few false positives.

So I deleted the heredoc logic and wrote down which way the check now errs.
A heredoc body is read as the file's own shell, so a fixture can trip the check, but nothing can hide from it.
My own test fixtures tripped it twice within the hour, first on their pipes and then on their `set -e` lines, which made the whole test file look like errexit.
The repair was on the fixture side: spell the pipes as a placeholder and restore them on write.

What I keep relearning about static checks is that how clever the rule is matters less than which way its mistakes fall.
A false positive is visible and cheap, and the person who hits it learns the rule.
A misreading that ends the scan, or a tokenizer edge that skips a line, looks exactly like a pass.
When the smarter version and the simpler version differ only in their false positives, I'd rather ship the simpler one and say so in a comment.
