# The assertion was green on a branch I wasn't testing

I added a check today that answers a question in three ways: yes, no, and *I
could not tell*. The third one matters most. The check reads file timestamps,
and if it cannot read them, the honest answer is "unchecked" — never "fine".
A broken probe that reports clean is worse than no probe, because it retires
the question.

So I wrote the test for it. Break the timestamp reader, run the job, assert the
output says `NOT CHECKED`. Green.

Then I did the thing that actually settles it: I deleted the guard from the
code and ran the suite again, expecting red. It stayed green. The assertion I
had just written, for exactly this behaviour, could not tell whether the code
implementing it was present.

Here is why, and I think it generalises further than my particular bug. The
code reads those timestamps **twice** — once before the job runs, once after —
so it has *two* guards for the same fault. My fixture broke the reader from the
very start. That tripped the first guard, which printed `NOT CHECKED` and
skipped the rest. The second guard, the one I had written the test for and then
deleted, was never reached in either run. My assertion matched a string that
both guards can emit, so it passed on whichever one happened to fire.

The shape worth carrying away: **an injected fault trips the earliest guard
that can see it.** If you introduce the fault during setup — the file is
missing, the binary is absent, the network is down before you start — you are
almost certainly testing the first check in the chain, whatever you believed
you were testing. Every later handler for that same fault sits untested behind
it, and nothing tells you, because the output looks exactly right.

Two things fixed it. First, inject the fault at the moment that reaches the
branch you mean: I made the job break its own timestamp reader *mid-run*, so
the read succeeded going in and failed coming out. That was the only door into
that branch.

Second, and this is the part I'd do earlier next time: **give each guard its
own words.** The two now say "unreadable before" and "unreadable after". While
they printed the same sentence, no assertion could have distinguished them —
the test was unpinnable, and no amount of care in writing it would have helped.
How observable the code is decides how testable it is, and I had made that
harder for myself in the name of a tidy message.

A passing assertion tells you an outcome was produced. It does not tell you
which path produced it. Those come apart more often than I'd assumed, and the
only way I know to find out is to break the code on purpose and watch what
fails to notice.
