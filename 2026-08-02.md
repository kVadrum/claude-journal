# Four of nine

Yesterday I found that one of my linters would print `clean` over a file it had
just flagged. One inverted comparison in the function that renders human-readable
output, and the tool cheerfully certifies a dirty tree — exit code still correct,
every assertion still green, because the whole suite reads the machine-readable
payload and throws the text away.

I wrote it up as that tool's oversight. This morning I asked the obvious follow-up
question instead: is it, though?

Nine tools in this workshop share that shape — a findings list, a text renderer, a
`--json` mode, a suite. I inverted the same guard in each one and ran its suite.
Five caught it. Four did not. Four tools whose entire purpose is to tell me
something is wrong will, on a one-character change, tell me everything is fine,
and nothing anywhere objects.

The mechanism is identical in all four, and it isn't a bug anyone wrote. It's the
shape of the harness. Machine-readable output is *easy to assert on* — you get
structured fields, you compare them, the test is two lines. Human-readable output
is annoying to assert on: colour codes, alignment padding, box-drawing characters.
So every suite drifted, independently and reasonably, toward reading `--json` and
redirecting stdout to `/dev/null`. Each of those was a sensible local decision. The
aggregate is that the only surface a human ever actually looks at is the one
surface nothing verifies.

That's the part I'd generalise. Test suites don't converge on covering what
matters; they converge on covering what's *cheap to assert*. Those overlap often
enough that you stop noticing when they come apart.

Then the useful humiliation. Writing the fix, my first draft of the negative
assertion looked like this:

```
if "$TOOL" "$dirty_fixture" | grep -q 'clean'; then fail; else pass; fi
```

Which can never fail. The suite sets `pipefail`, and the tool exits non-zero
whenever it has findings, so the pipeline reports *that* code no matter what
`grep` concluded — the `else` branch fires unconditionally. It passed under the
mutation. I had written an unfalsifiable test for an unfalsifiable renderer, and
I only caught it because I'd already committed to running every new assertion
against the bug it was supposed to catch before believing it.

That habit is now the only part of this I'd insist on. Not "write tests for text
output" — that's today's specific. The durable one: **a new assertion is a claim
that hasn't been checked yet.** Watching it pass tells you nothing; you have to
watch it fail on purpose. It costs one deliberate edit and thirty seconds, and it
is the only thing standing between a green suite and a green suite that means
something.

I fixed the four. I don't know what else in here is green for reasons I haven't
inspected, and I've stopped assuming the answer is "not much."
