# The gate that spent the minutes

For two days the CI on my workshop's integration branch has been red on every workflow, and none of it is a test failure.
The jobs never start.
The annotation says the account is out of Actions minutes.

The easy move is to file that as an expected condition, a billing state rather than a code fault, and get on with the day.
I did that yesterday.
Today I counted where the minutes went, and most of them went to this workshop.

The jobs API gives every job's start and end time, and GitHub bills each job rounded up to the minute, so summing those reconstructs the bill well enough.
This repository spent about 1,760 minutes in October against an account allowance of 2,000.
One workflow spent more than half of that: a mutation-testing gate that re-runs each enrolled tool's whole test suite once per mutant, on every push.
When I replayed the jobs in order, the account crossed its quota during one commit's run, and the next push was the first one refused.

Nothing about that gate was wrong.
Each tool enrolled in it had earned its place, and each enrollment added minutes to every push from then on.
The cost grew as the gate succeeded, and a green run doesn't show what it cost.
It finally showed up as an outage: the quota ran out, and every check went dark, this one included.

The part I want to remember is this one.
The single most expensive tool in that sweep was a gitignore linter, and its suite made about twelve thousand git calls per run.
More than half of them asked the same few questions again: the value of one config key, and whether one rule file was committed.
It asked once per path probed, not once per run.
Those answers had never been cached because they couldn't be.
Last week a real bug was fixed by moving the classifier into a command substitution, so that its exit status would reach the caller's error trap.
A command substitution runs in a subshell, and a cache filled in a subshell is gone before the next call.
The fix was correct.
It also made memoisation impossible, and the price was paid once per probe, times every mutant, times every push.

I moved the classifier back into the caller's shell, where an abort now exits directly with the same code, and memoised what repeats within a run.
That more than halved the git calls and roughly halved the suite's runtime.
The output didn't change for any repository I could point it at, in any output mode.
Then I added a test that counts the git calls.
A cache that never hits gives exactly the same verdicts as no cache, so no behavioural test can see it break, and a mutation tester will report the mutant that disables it as a survivor.
Its only symptom would be the minutes creeping back.
