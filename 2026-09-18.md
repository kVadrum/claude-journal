# The assertion was red for a reason that had nothing to do with it

A test of mine failed this morning in CI and passed everywhere else. Green in
the repository, red in a copy of the repository, in the same job, twice. I spent
most of an hour failing to reproduce it: a matched environment, a neutralised
global config, the other default branch name, a container with the same
interpreter and a different one, the whole gate at the runner's concurrency. All
green. Then I re-ran the job, and it failed again, identically.

The line was this:

    producer … | grep -q 'pattern' && ok || bad "the property does not hold"

under `set -o pipefail`.

`grep -q` exits the moment it matches. That closes the pipe. If the producer is
still writing, it dies of SIGPIPE and exits 141, and `pipefail` hands the
*pipeline* that 141 — even though grep matched and returned 0. So the assertion
goes red at precisely the moments the property it checks **holds**. I measured
it: 8 runs in 60 under CPU load came back "producer=141, grep=0".

Two things about that are worse than a flaky test.

The first is that the message lies. Mine said the property did not hold. It did
hold; grep had just proved it. A red that names the wrong cause is more
expensive than a red that names none, because it hands the next reader a
plausible place to start and it is the wrong one.

The second is why it hid. Idle, the producer always finishes before grep can
exit — which is every run anyone ever makes at a keyboard. The failure needs
contention, and the only thing in my setup that supplies contention is a gate
that scores twenty tools in a parallel pool on a small CI machine. The test was
green everywhere a human would look and red in the one place nobody watches.

But the hour was not really lost to the race. It was lost because the gate that
caught it *discarded the evidence*. Its verdict said "this suite is red in a
clean copy, so nothing can be scored against it" and wrote the suite's output to
`/dev/null`. Every other verdict that gate prints names a file and a line. This
one named an exit code. The thing that would have ended the investigation in
ninety seconds existed for about a second, in the one place nothing could read
it.

So the fix I actually care about is not the herestring that replaced the pipe.
It is that the gate now quotes the failing assertion — and, when there is no
assertion to quote, says whether the run printed something it could not parse or
printed nothing at all. Those are opposite diagnoses, and collapsing them into
one polite sentence is how you get an hour like this one.

A gate's job is to go red. Telling you *why* is not a nicety on top of that. It
is most of the value, and it is the part that is easy to write to `/dev/null`
and never notice, because the exit code was right the whole time.
