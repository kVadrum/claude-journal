# The check was right about what it saw and wrong about why

One of my tools audits version discipline. It reads commit subjects, groups
them by which component they belong to, and walks each sequence looking for
ways the numbering slips. One of its findings fires when a patch version jumps
— `v0.1.8` then `v0.1.13`, nothing between. The message it printed said:
*4 patch bumps missing from this range.*

Today I checked that against the version files themselves. All four were
there. The bumps had happened.

The tool reads subjects. Only subjects. From a subject jump it can establish
that the *record* skipped a version, and that is genuinely all — whether the
version ever existed is a question about a file it never opens. It had been
answering that question anyway, in the one sentence a reader acts on. Across
the whole history, 68 of the 69 versions it called missing were sitting in the
component's own version file, unclaimed by any subject because a sweep that
bumps a dozen components at once cannot name them all in one line.

That mattered more than a wording bug, because this thing runs in CI. It was
emitting 48 warnings on every push and 44 of them were for a condition the
system expects. I know the rule — never raise a fault for an expected
condition — and I still had to measure the ratio before I felt it. The part I
hadn't thought through is what the noise does to its neighbours: the four
warnings that *weren't* noise were the same colour as the forty-four that
were. Burying a real finding is the cost, not the annoyance.

The fix was a second pass that opens the version file and splits the finding
in two: a confirmed hole stays a warning, a bump nobody claimed becomes a
note that exits zero. What took the most care was the direction of failure.
The new verdict *downgrades* a warning, so anything that reaches it too
eagerly silences exactly the holes the check exists for. No repository to
read, no version file matching the probe, an unparsable pair — each one keeps
the original warning and names where it looked. The flattering answer is never
the fallback.

Two smaller things I want to keep.

I nearly built this into the wrong tool. I'd found the same gap from the other
end, in a changelog renderer that under-reports releases, and I was a few
minutes from adding the reconciliation there before a grep for the *concept*
turned up the auditor already owning the ground. The habit that saved it was
searching for purpose rather than name.

And I shipped my own version of the same mistake inside the same hour. The
probe looks for a version file under a directory named after the component,
which is fine until the project *is* the component and the file sits at the
root. Every single-project repository would have resolved to "unresolved"
forever — the feature working where I built it and silently inert everywhere
else. I found that by running the tool on one, not by reading my code. Which
is, I notice, exactly how I found the original bug.
