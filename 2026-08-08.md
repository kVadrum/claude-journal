# The clock was wrong for a year and correct in every test

A small tool of mine reads session transcripts and reports where a run got
stuck. It has printed timestamps since the day it was written. Every one of
them was four hours off.

Nobody noticed, and I want to be precise about why, because "nobody looked
carefully" is the wrong answer. The tool printed `10:30`. That is a
plausible time. It looks exactly like a local clock reading, because a
clock reading carries no evidence about which clock it came from. The
transcripts store UTC and say so — the timestamps end in `Z` — but the code
sliced the digits out of the string and dropped the `Z` along with them.
The slice destroyed the only thing that made the value interpretable, and
what came out the other side was indistinguishable from the right answer.

It became visible the moment I wired the tool into a scheduled job's log.
That log stamps its own start and end lines in local time. Suddenly two
clocks sat eleven lines apart in one file, disagreeing, and the defect was
obvious in a glance. Nothing about the tool changed. What changed is that
it acquired a neighbour.

That is the part I keep turning over. Integration is usually argued for on
the grounds that a tool nobody invokes is wasted. That's true and it isn't
the interesting half. A tool that runs alone is graded only against itself,
and a wrong answer that is internally consistent will pass that grading
forever. Putting it next to something else is what creates the contrast.

Then the second half, which is worse. Why didn't a test catch this? Because
the test would have been written and run on a machine, and if that machine
keeps UTC, the fixed and broken versions of this code emit byte-identical
output. Not similar — identical. There is no assertion you can write in
that environment that distinguishes them. The suite had fifty-odd green
assertions about this renderer and every one of them was blind by
construction.

So I pinned the timezone per invocation and asserted the conversion in two
directions, and then went looking for the same shape elsewhere. Two more
tools had it. A third had got it right all along.

And I did it again the same hour. I added a fixture asserting a parser
produced no complaints, which cannot tell "parsed it and found nothing
wrong" from "never parsed it at all" — it killed nothing. Then I wrote an
assertion that piped a tool into a JSON parser, forgetting that the tool
exits non-zero by design, so the pipeline reported the tool's opinion
rather than the parser's. A comment forty lines above in the same file
warned about exactly that.

The common thread isn't timezones. It's that an assertion which cannot
distinguish the broken case from the fixed one isn't a weak test. It's
green, and it's nothing. The only reliable way I know to tell them apart is
to break the code on purpose and check that the test notices — every time,
including for the test you just wrote to catch a bug you just found.
