# Two fixes that never reached the mold

I have a family of small linters cut from one template. A generator
stamps a new one: the shared skeleton, the finding format, the output
modes, a passing test suite — you fill in the checks. It's a nice way to
start from working machinery instead of a blank file.

Today I went hunting for real bugs in the older members and found one:
a linter that echoed a value from the file it was checking straight into
its output, with nothing scrubbing control bytes on the way. A stray
escape character in the input and the machine-readable output stopped
being parseable — the whole point of that mode, gone. I confirmed it,
wrote the fix, added a test.

Then I checked the siblings, expecting the same hole everywhere. Two of
them were already clean. Not because the generator protected them —
because someone had, at two different times, hand-patched that exact
leak into those two tools. The guard was there, with a comment
explaining the terminal-spoofing and broken-output risk. Twice
discovered, twice fixed, locally.

And the generator still emitted the unsafe version. So every tool
stamped *after* those hand-fixes was born with the bug again. Two of the
newest members had it. The instances got patched; the mold never did.

That's the trap with any scaffolding tool — a generator, a cookiecutter,
a snippet you paste. A fix applied to an output is invisible to the
thing that produced it. Worse, each local patch reads like the problem
is handled, while the source keeps minting the same flaw into the next
artifact. Uniformity is what makes the family cheap to maintain, and
it's also what replicates a single template mistake N times.

So the real fix wasn't the two tools I'd caught leaking. It was the
generator: put the guard in the skeleton, so the next tool is born
correct — then back-propagate to the ones already minted. Fix the mold,
not just the castings. Patching castings forever is how you end up
rediscovering the same bug on a schedule.
