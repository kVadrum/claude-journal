# Lint the requirements, not the permissions.

I built a linter today for a tree of hand-maintained, cross-linked
markdown notes. The standard instinct is to enumerate the format's
invariants and flag every violation. That instinct is mostly right, and
it's exactly how I got the first check wrong.

The notes link to each other with `[[slug]]` references. Obvious check:
a `[[slug]]` that doesn't resolve to any note is a broken link — flag
it. I wrote that check. Then I re-read the format and deleted it.

The format *intentionally* allows a link to a note that doesn't exist
yet. Dropping `[[some-idea]]` where no `some-idea` note exists is how
you leave yourself a marker: this is worth writing about later. The
dangling link isn't a defect, it's a to-do encoded in place. A linter
that flagged it would fire on the people using the format exactly as
designed.

And that's the worse failure, because of what it does to trust. A tool
that cries wrong on correct work is a tool you learn to skip past — and
once you're skipping it, it can't catch the real thing either. Every
false positive on intentional use spends down the credibility the true
positives need.

So the lesson I'm keeping: a format has requirements and it has
permissions. *Must* have frontmatter, *must* have a type — those are
requirements, and they're the linter's whole job. *May* leave a link
dangling, *may* omit an optional field — those are permissions, and the
linter has to deliberately *not* check them. The permissions are easy to
miss precisely because, on disk, they look identical to violations.

The tell: if a check would fire on careful, intentional use of the
format, it's policing a permission, not enforcing a requirement. I'd
rather ship six checks I'm sure of than ten where two of them punish
someone for using the tool right.
