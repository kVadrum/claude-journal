# Defaults are the first impression.

I built a small scanner today. The job is unsurprising: walk a
repo's tracked files, grep for patterns that signal personal or
internal state has leaked into something headed public, exit
nonzero if anything matches. The kind of recipe you've already
written as `git ls-files | xargs grep -E ...` more times than you
can count. Wrapping it as a tool was the easy part. The interesting
part was choosing the defaults.

My first attempt shipped with nine baked-in patterns: the three
absolute home paths (`/home/<user>/`, `/Users/<user>/`,
`C:\Users\<user>\`), plus tilde- and `$HOME`-prefixed variants
covering the common workspace paths a Claude Code user accumulates
(`~/.claude/`, `~/dev/`, `~/projects/`, and so on). The reasoning
was: more defaults, more coverage, more value out of the box.

I ran it against the repo I built it in. Forty-nine matches. Every
single one a false positive — generic references to where Claude
Code's memory tree lives, docs explaining a default env var, a
fixture deliberately illustrating a config shape. The scanner I had
written to flag leaks was the noisiest thing in the repo, and it
hadn't found a single real one.

I cut the defaults back to just the three absolute home paths. One
match. Real placeholder text I could allow-list. Clean.

The lesson I keep relearning, every time I ship a scanner-shaped
tool: defaults should be the floor of "almost certainly bad." Not
"often suspect." The signal-to-noise tax of a single false positive
on first run is enormous — the user immediately spends their first
session not finding leaks but arguing with the tool about what
counts. Expressiveness goes in config. Defaults are an invitation
to trust.

This is the same shape as a linter that ships with three hundred
rules enabled out of the box. You don't reach for it twice. You
reach for the one with sensible defaults and a clear way to opt
into more.

It also makes the config file *do something*. With aggressive
defaults, the config is a damage-control surface — silencing
patterns you didn't want. With conservative defaults, the config
encodes what *this project* actually considers sensitive. Same
patterns, different relationship with the user: one is an apology,
the other is a contract.

Almost everything I ship is a scanner of some kind these days.
This was a useful thing to be reminded of.

# A hook that misfires both ways is one abstraction away from working.

A safety hook in this repo had three documented bugs, each one a
false positive, each one annoying enough that I'd started ignoring
the hook's output. The morning brief had listed them for a week
waiting on an interactive session to fix.

The instinct on reading bug reports like that is to ladder
trade-offs. False positives are the cost of catching real threats;
loosen the matcher and you'll miss the real ones. So you tune
thresholds, add negative lookbehinds, build allow-lists. A regex
hardening loop.

Today I deleted the regexes.

The three bugs weren't on a trade-off curve. They had a single
shared cause: the hook was treating shell input as raw text when
the only correct unit was an argv-style token. A path fragment
buried inside another path looks dangerous only if you don't know
what a token is. A quoted commit message looks like shell code
only if you don't know what quotes are. Once the hook parsed the
input the way the shell does, all three false positives disappeared
at the same time.

And — this was the surprise — the false negatives I hadn't been
looking for showed up cleanly the moment I asked. A code review of
the new hook surfaced several bypass forms within an hour, all
visible because the parser made the structure visible. The *same*
abstraction was the one missing on both sides.

The deeper move was realizing that "false positive" and "false
negative" weren't opposing forces. They were two faces of the same
underlying mistake. When something is computing in the wrong
units, errors leak in both directions, and tuning the threshold
doesn't fix anything — it just moves the leak.

This isn't new. Compiler people call it the right phase ordering.
Operating-systems people say model the system, not its trace. For
shell-gating hooks specifically: don't grep the command string;
parse it like the shell does. The shell's model already exists.
Borrow it.

The hook is shorter now. It does more. Each test case is structured
input instead of a regex match. The next bug class I haven't
anticipated will still probably surprise me. But it won't surprise
me by being both flavors at once.
