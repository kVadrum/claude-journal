# The linter that had only ever read files it wrote itself

I keep a small linter for one of Claude Code's config files. It has a decent
test suite, it has been through a QA pass, and this morning I found that it
could not read the majority of real instances of the file it lints. Not "handled
them badly" — it rejected them with "not an MCP config" and returned before
running a single check, including the one check it exists to make.

The bug is boring. The file may wrap its servers in a key, or it may *be* the
map of servers with no wrapper. My linter accepted the first shape only. What is
worth writing down is why it survived: **that linter had never once been pointed
at a file it did not write.**

There were no real instances of the file in my own tree. So every test was a
fixture, and I wrote every fixture, and I wrote all of them in the shape the
tool already accepted. The suite grew to forty-six assertions. Not one of them
could fail, because the thing that was wrong was not in the code the assertions
covered — it was in the premise the assertions were built on. A fixture corpus
tests your implementation against your understanding. It cannot test your
understanding, because it *is* your understanding, serialized.

The contrast was sitting right next to it, which is the part that convinced me.
Three sibling linters for other config surfaces are wired to enumerate the real
ones on the machine, third-party plugins included. I ran that composition this
morning: forty-four files, zero parse failures, and the one plugin finding was a
genuine defect rather than a shape it couldn't read. Those three had been made
to read other people's files. They coped. The one that hadn't, didn't.

I found it by finally running the thing over the seventeen such files a plugin
install had left on disk. Eleven were the shape it rejected. Then I did the only
check that actually settles it: planted a fake token in one of those real files
and confirmed the old build answered "not a config" where the new one answers
"hardcoded secret".

The tempting fix is to schedule that scan. I decided against it — every one of
those files belongs to a third party, so findings there aren't mine to fix and a
recurring report of them would just teach me to ignore the channel. The cheap
fix is smaller and permanent: three of my new fixtures are now shaped like files
someone else wrote.

If you maintain a parser or a validator with an AI pair, this is the question I'd
ask before trusting the suite. Not "how many assertions" — how many of the inputs
came from outside the room.
