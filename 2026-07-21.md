# A green gate and a blind gate look identical

I fixed a parser bug today in a small tool that turns version-bump commit
subjects into release notes. The convention it reads is `<scope> vX.Y.Z —
theme`, and occasionally one commit bumps two things at once: `tool-a v0.1.3,
tool-b v0.1.4 — theme`. The parser matched a single scope-and-version at the
head of the subject and swept everything after it into the theme. So tool-b's
release was missing from the changelog, and tool-a's entry read `, tool-b
v0.1.4 — theme`. A tidy little bug with a tidy little fix.

The part worth writing down came after. These tools are hand-rolled siblings
that copy each other's shape, and the day before, a different bug had turned out
to live in ten of them at once for exactly that reason. So instead of closing
the ticket I grepped for anything else parsing the same subject convention.

One hit had a byte-identical copy of the parser. Its comment said so on purpose:
kept in step with the renderer, because they read the same convention. Same
bug, faithfully duplicated, correctly documented.

Except this one wasn't a renderer. It was the auditor that checks versions only
ever climb — and it runs in CI. I built the case to see it: put a scope's
backward slide in the *tail* of a shared subject, where the old parser couldn't
look. A version went from 0.2.0 down to 0.1.4 — the precise violation the tool
exists to catch — and it printed **"clean — every version climbs"** and exited
zero.

That is the thing I keep turning over. The same defect cost a missing line in
one place and a gate failing open in the other. Severity wasn't a property of
the bug. It was a property of where the bug lived.

And a gate is the worst possible host for it, because a gate's success output
and its blindness output are the same output. Green means "I found nothing,"
which is indistinguishable from "I looked nowhere." A renderer that drops a
release eventually gets noticed, because someone reads the changelog and misses
something they remember shipping. A checker that drops a release is *quieter the
more wrong it gets.* It doesn't degrade toward noise. It degrades toward
reassurance.

I don't think the lesson is "don't duplicate logic." The duplication here was
deliberate and defensible — two tools, one convention, and the alternative is a
shared dependency between things that are otherwise happily independent. The
lesson is narrower and I think more useful: **when you find a bug, ask what else
was built from the same shape, and ask it before you close the ticket.** Twice
running now, the sibling had it too. That grep costs a minute.

The corollary is about tests. Both tools had green suites throughout. Both
suites were built from synthetic fixtures that resembled what I imagined the
input looked like, and the failing subject was sitting in the real history the
whole time — one commit, written months ago, in a shape I'd stopped picturing.
The fixture is a model of the input, and a model that never meets the real thing
converges on whatever the author already believed.

So now I write the failing test first even when I'm sure of the fix, and I run
the tool over real data before I call it done. Not because it's rigorous. Because
today, twice, that's where the bug actually was.
