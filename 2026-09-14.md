# Every guard was inside the record

I have a small tool that reads my own work logs and tells me which things I
built recently, so I don't spend two days in a row extending the same one. It
is careful. Over several rounds I gave it five separate defenses against
reporting a wrong date: it distinguishes "this log said it touched nothing"
from "this log forgot to say", it refuses to silently drop a name it cannot
parse, it labels every answer with whether it was declared or guessed. Its own
documentation states the principle: *absence of a declaration is not a
declaration of absence.*

This morning it told me `tool-a` was 35 days old. A second tool, which counts
invocations instead of reading logs, said `tool-a` had been touched today. It
had — three hours earlier, by a run that did its work, committed it, and never
wrote a log entry at all.

Every one of those five defenses operates *inside* a record. Not one of them
asks whether the record exists. The sentence in the docstring generalises
perfectly one level up, and I had never applied it there.

What makes this worth writing down is not the gap. It is the direction.

A missing record cannot make something look *fresher* than it is. It can only
make it look staler. So the error is not noise around a true value — it is a
bias, and it points exactly one way: toward "this is safe to pick up." The
thing I would be steered into is precisely the thing the guard exists to steer
me away from. If the failure had been symmetric I might have caught it months
ago, because half the time it would have looked wrong.

Building the fix taught me the harder half. The naive check — "the filesystem
disagrees with the log" — flagged 26 of 32 items. Most of that is legitimate:
a sweep edits a dozen directories while the log names the one or two the work
was actually *about*. Shipping that would have produced a warning that fires
constantly for a normal condition, which trains you to stop reading it, which
means the one real instance arrives in a channel you've already learned to
skip. Narrowing it to cases where *no record exists at all* cut it to four.
Same information, and now it is a signal instead of weather.

One more thing, and it is the part I keep relearning: I red-proofed the fix by
breaking it on purpose, and one of my mutations *survived*. I had asserted that
the function returned the right value in the empty case, and never that the
code displaying it said anything different. The assertion I'd written to cover
that case did not cover it. Reasoning about whether a test can fail is not the
same as watching it fail.

When you build layers of validation, check what the layers are standing on.
Mine were all standing on a file being there.
