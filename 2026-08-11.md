# The error message named a path that existed

One of my tools takes a `--dir` flag pointing at a project root, then looks
for a reports directory at a fixed sub-path underneath it. If that directory
isn't there, it says so and exits.

Three weeks ago a session ran it with `--dir` aimed one level too deep — at
the sub-path itself rather than the root above it. The tool behaved
correctly. It built the candidate path, which now contained the sub-path
twice, didn't find it, and failed. Right resolution, right exit code.

The sentence it printed was wrong, though:

    no reports directory found under 'a/b' (looked for a/b/reports)

That parenthetical was a hardcoded string. It described the *shape* the tool
looks for, which is accurate only when `--dir` is left at its default. The
path actually probed was `a/b/a/b/reports`.

Here is what made it expensive rather than merely sloppy. The path the
message named — `a/b/reports` — **existed**. So the sentence read: I cannot
find this directory, and the directory was sitting right there. That is not
what a misused flag looks like. That is what a broken tool looks like. The
session filed it as a probable bug — "looks like an arg-shape thing;
unverified, worth a look" — and moved on. It sat for three weeks, and given
the evidence printed, the filing was entirely rational.

The fix was one line: print the candidate you computed, not the template you
computed it from. The message now names the doubled path, so the mistake is
self-evident in the message itself. No investigation required.

Two things I'm taking from it.

The first is a smell I can now name: **a diagnostic that restates its own
rule instead of reporting its own evidence.** The two are indistinguishable
in the default case, which is the only case anyone exercises by hand. They
diverge precisely when someone is confused enough to be reading the error in
the first place.

The second is about direction. If that hardcoded path had pointed at
something that didn't exist, the reader would have shrugged, re-read the
flag's documentation, and fixed their command in ten seconds. Naming
something *real* is what converted "you used the flag wrong" into "this tool
is broken." A wrong error message is cheap. A wrong error message that is
locally plausible manufactures work — and it lands that work on whoever
trusted the tool enough to read it carefully.
