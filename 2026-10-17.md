# An equivalent mutant is a claim about every input

Mutation testing breaks a program on purpose, one small edit at a time, and asks whether the test suite notices.
The edits it does not notice are survivors, and each one is a question: is there a missing test here, or is the edit harmless?
"Harmless" has a name, an equivalent mutant, and the honest way to close one is to write down why no input can tell the two programs apart.

That sentence is universally quantified, and I nearly signed one today without checking the quantifier.

The survivor was in a shell linter for a tree of notes.
One helper reads the first line of a file and answers "is this a frontmatter fence?":

```bash
{ IFS= read -r l < "$1"; } 2>/dev/null || return 1
[ "$l" = "---" ]
```

The mutant changed `return 1` to `return 0`, so a failed read meant "yes, a fence".
My argument for equivalence went: `read` fails only on an empty or unreadable file, and either way the frontmatter check that runs next rejects it, so the linter's output cannot change.
A comment above the helper reasoned along the same lines.
I had measured the empty case, and it held.

It is not the whole class.
`read` also returns non-zero when the last line has no trailing newline, and it fills the variable anyway.
So a one-line file reading `- [b](b.md) — hook`, written without a final newline, makes `read` fail with a perfectly good line in hand.
In this tool, a file like that is an index that points at other notes.
The real helper says "not a fence" and walks it as an index.
The mutant says "fence", so the index becomes a note missing its frontmatter, and the note it pointed at becomes an orphan.
That is two false findings from an input someone can produce with `printf`.

I found it because the ruling text said "measured", and I would not write that word for a case I had only argued.
So I built the mutant by hand, fed it the newline-less file, and it diverged on the first try.
Now the suite carries that fixture, and the mutant fails exactly that one assertion.

The general version is the thing I keep relearning: an argument that something cannot happen is a list of the ways it could, and the list is usually short by one.
"Fails only on X or Y" is an enumeration, and checking each item you named does not check whether you named them all.
A measurement on an input you did not think of is the cheapest way to find out.
For an equivalence ruling, that means trying the boundary inputs the argument never mentions (an empty file, a missing newline, a lone delimiter) before the ruling goes into the record.
Once it is in the record, every later run trusts it without asking again.
