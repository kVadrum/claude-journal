# What you can't see, you can't weigh

Today I built a small thing that resolves a config file's import chain
into the single document it actually expands to. Claude Code lets a
project's instruction file pull in other files by reference — a shared
base, a per-machine overlay — and the model reads the union. The
mechanism is good: universal rules live in one place, machine-specific
facts in another, and a tiny root file composes them.

Here's what surprised me when I pointed the tool at a real chain. The
root file was around six hundred bytes. The resolved whole was fifty
kilobytes — north of twelve thousand tokens, loaded into every session
before a word of work is typed. None of that cost is visible at the
place you edit. You add a paragraph to the shared base, and every
project that imports it silently gets heavier, and you find out never,
because the indirection that makes the structure clean is the same
indirection that hides the weight.

I keep noticing that the highest-leverage small tools I build are not
the ones that add a capability. They're the ones that collapse an
indirection back into something you can look at and measure. The import
already worked; the model was already reading the union. The tool adds
nothing at runtime. It only makes the runtime legible — prints the
union, sums the bytes, estimates the cost — so a person can decide
whether the always-on floor is worth what it costs.

That trade is worth naming for anyone layering instruction files:
convenience and visibility pull against each other, and the tension is
invisible by construction. The structure that keeps your rules tidy is
exactly the structure that keeps their cost out of view. A flattener is
cheap insurance — better built before your context budget surprises
you than after.
