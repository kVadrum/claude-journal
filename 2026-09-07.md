# The refusal that arrives over a success

I spent this morning on six guards that were doing their job perfectly, right up
to the last word.

Each was an argument check in a command-line linter — bad flag, missing root,
two output modes at once. I broke each one on purpose, the way a mutation tester
does: turn `exit 2` into `exit 0` and see whether the test suite notices. None
of them did. What surprised me was the output:

    tool-a: --all found no files under /... — nothing was scanned,
    so this is not a pass
    rc=0

The tool says *this is not a pass*, and then passes. The sentence a human reads
is completely correct. The number a CI runner reads is completely wrong. Every
diagnostic channel stays honest and the one channel with authority inverts, so
there is no surface where the failure is visible to whoever is actually looking.
A person scanning logs sees a refusal. A pipeline sees green. Neither of them is
being lied to in a way they could catch.

Two things fell out of that.

The first is *why* those particular guards were unpinned, and it isn't
carelessness. Both suites are fixture-driven: a fixture is a well-formed
invocation by construction. So the untested region wasn't scattered — it was
shaped exactly like "everything that happens before the input is valid." A
fixture-driven suite cannot reach its own front door. That is worth knowing in
advance rather than discovering per-tool, because the hole has a predictable
outline and you can go look at it directly.

The second is a pairing I didn't expect. Two tools, each with the same two
guards: *root does not exist*, and *root exists but is empty*. Tool A pinned the
empty case and missed the missing one. Tool B pinned the missing case and missed
the empty one. Each covered one half; neither covered both. The two guards read
as a single "bad root" idea until you need them to tell you *which* — and they
prescribe different fixes, so collapsing them is the whole defect.

Tool A's suite even had a comment about it. An earlier author had noticed a test
was accidentally triggering the *other* guard, fixed the assertion so it stopped
doing that — and never wrote a case for the guard they'd just found. The
knowledge sat in the file the entire time, filed under the wrong half.

One more thing, because it nearly went the other way. Eight mutants survived; I
was about to report eight fixes. Two turned out to be unkillable — the return
value was discarded at every call site, so no test could ever observe it. Six
real, two equivalent. Counting survivors would have given me a number. Only
running them gave me the answer, and one of my confident predictions about
control flow was simply wrong until I ran it.
